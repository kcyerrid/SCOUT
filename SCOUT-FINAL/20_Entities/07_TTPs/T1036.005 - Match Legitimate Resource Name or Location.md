# Masquerading: Match Legitimate Resource Name or Location (T1036.005)

## 1. Summary
Match Legitimate Resource Name or Location describes adversaries **placing malicious files, services, or processes in directories and paths commonly associated with trusted system or application resources**, or using names that closely resemble legitimate components. This technique exploits defender assumptions about trusted locations.

Attackers use this technique to:
- Blend malicious artifacts into trusted filesystem locations
- Evade path-based detections and triage heuristics
- Reduce analyst suspicion during investigations
- Increase persistence and dwell time

---

## 2. Technical Overview
Defenders often implicitly trust binaries and scripts located in specific directories. Adversaries abuse this by:

- Placing malware in system or application directories
- Using directory structures similar to legitimate software
- Matching naming conventions used by trusted applications
- Leveraging user profile paths that commonly host executables

Commonly abused locations include:
- System directories
- Application installation paths
- User application data directories
- Cloud workload and container file paths

Indicators include:
- Executables appearing in trusted paths without installation context
- Files in system directories lacking valid signatures
- Execution from locations inconsistent with host role
- Path-based trust assumptions being violated

---

## 3. Subtechnique Considerations
Key considerations for T1036.005:
- Often paired with **Hide Artifacts (T1564)** and **File Deletion (T1070.004)**
- Can overlap with **Masquerading via Naming (T1036)** broadly
- Particularly effective against static path allowlists
- Requires defenders to validate both **what** and **where**

This technique is **context-dependent**, relying on environmental trust models.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Placing malware in directories typically reserved for system binaries
- Deploying payloads in application folders to appear legitimate
- Using directory naming patterns that mimic installed software
- Executing malware from paths normally excluded from scrutiny

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should focus on **path legitimacy and provenance**:
- Monitor file creation in trusted directories
- Detect execution of unsigned binaries from system paths
- Correlate file placement with installation or update activity
- Alert on unexpected binaries in application directories

### Data Source Notes
- **File system monitoring**: Detect file creation and movement
- **Image load telemetry**: Identify binaries executing from trusted paths
- **EDR telemetry**: Provide provenance and lineage

Common false positives:
- Legitimate software updates
- Enterprise deployment tools
- Custom internal applications

Tuning guidance:
- Maintain inventories of approved binaries per directory
- Increase severity when path abuse coincides with suspicious execution

---

## 6. Response Guidance
When suspected:
1. Validate file origin and installation context
2. Check digital signatures and hashes
3. Analyze execution behavior and lineage
4. Remove unauthorized binaries safely
5. Hunt for similar artifacts across systems

## 8. SOC Relevance
T1036.005 is highly relevant when:
- Malware is found in locations typically considered trusted
- Path-based allowlisting is bypassed
- Analysts initially discount artifacts due to location

SOC teams must validate **location trust assumptions**.

## 12. Mitigations
Recommended mitigations:
- Enforce strict application allowlisting
- Monitor trusted directories for unauthorized changes
- Validate signatures for binaries in system paths
- Restrict write access to trusted locations

---

## 13. Testing & Validation
Validation approaches:
- Place benign binaries in trusted directories in lab environments
- Validate alerts on unauthorized file placement
- Test SOC workflows for path-based masquerading
