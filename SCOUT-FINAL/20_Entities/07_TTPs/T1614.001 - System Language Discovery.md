## 1. Summary
System Language Discovery is a Discovery sub-technique used to identify a host’s language/locale settings (e.g., UI language, keyboard layouts, `$LANG`) to infer geography, select payloads, tailor lures, or implement region-based execution guards (often to avoid local law enforcement scrutiny).

## 2. Technical Overview
Common collection methods vary by OS:
- **Windows**: locale/keyboard APIs (e.g., UI language functions, keyboard layout enumeration) and/or registry reads (e.g., `...\Control\Nls\Language`).
- **macOS/Linux**: querying locale configuration (`locale`, environment variables like `$LANG`), or OS-specific settings stores.
- **Browser/HTTP context**: language hints via headers (e.g., `Accept-Language`) when discovery is performed from an implant that makes web requests.

This activity frequently appears early in execution, sometimes immediately before payload staging, C2 selection, or conditional exit.

## 3. Subtechnique Considerations
- This is a sub-technique of [[20_Entities/07_TTPs/TA0007 - Discovery/T1614 - System Location Discovery|T1614]] and should be evaluated alongside other location inference checks (time zone, geolocation services, cloud region/zone metadata).
- **High-signal contexts**: language checks performed by unsigned binaries, scripts, or LOLBins; repeated checks across many hosts; checks immediately following initial access or before encryption.

## 4. Procedure Examples
- Multiple ransomware families implement **language/keyboard layout gating** to avoid running on specific locales.
- **[[30_CIPHER/03_Threat_Actors/G0032 - Lazarus Group|Lazarus Group (G0032)]]** used locale-related checks during **C0022 - Operation Dream Job** to prevent execution on specific language settings.
- Malware such as **[[30_CIPHER/05_Malware/S0446 - Ryuk|Ryuk (S0446)]]** has been observed querying Windows language-related registry values.

## 5. Detection Guidance
Prioritize detecting **who** is performing the query (process ancestry, signer, prevalence) over the query itself.

Detection ideas (defender-safe):
- **Windows registry access** to language/locale keys by unusual processes, especially shortly after initial execution.
- **API telemetry** / ETW / EDR sensor detections for locale/keyboard enumeration APIs invoked by non-standard binaries.
- **Command execution** patterns for locale inspection on macOS/Linux (`locale`, reads of locale config) initiated by unexpected parents (office apps, browsers, archive utilities, LOLBins).

### Data Source Notes
Useful telemetry typically includes:
- Process creation (image, command line, parent chain)
- Registry key/value access (Windows)
- OS API execution / user-mode API telemetry (EDR/ETW)
- Command execution (shell history, auditd, PowerShell logs)

## 6. Response Guidance
1. **Triage execution chain**: identify initial process and parent lineage; validate signer/reputation.
2. **Scope**: hunt for the same locale/keyboard query patterns across endpoints in the same time window.
3. **Contain** if tied to suspicious unsigned tooling: isolate host, block hash/path, and restrict outbound where appropriate.
4. **Follow-on hunt**: look for immediate subsequent behaviors (credential access, persistence, staging, encryption, or C2 beacons).

## 12. Mitigations
This technique is typically **not easily preventable** because it abuses legitimate OS features. Focus on:
- Application allowlisting / code-signing enforcement where feasible
- Hardening script execution (PowerShell Constrained Language Mode, macOS/Linux execution controls)
- EDR coverage for registry/API discovery patterns and anomaly-based detections

## 13. Testing & Validation
- Atomic Red Team test: https://www.atomicredteam.io/atomic-red-team/atomics/T1614.001  
Validation approach:
- Execute in a lab and confirm collection of process creation + registry/API telemetry.
- Ensure detection rules distinguish benign locale queries (IT scripts) from suspicious lineage (unknown binaries, user-writable paths).
