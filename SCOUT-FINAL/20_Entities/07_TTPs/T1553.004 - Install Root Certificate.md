# Subvert Trust Controls: Install Root Certificate (T1553.004)

## 1. Summary
Install Root Certificate describes adversaries **adding a malicious or attacker-controlled root certificate to a system or environment trust store**, allowing them to intercept encrypted communications, sign malicious code, or bypass certificate validation. Because root certificates are implicitly trusted, this technique enables broad and stealthy abuse of trust relationships.

Adversaries use this technique to:
- Perform TLS/SSL interception and man-in-the-middle attacks
- Make malicious binaries appear legitimately signed
- Suppress certificate warnings for attacker-controlled infrastructure
- Undermine encrypted communication guarantees

---

## 2. Technical Overview
Operating systems and applications rely on trusted root certificate authorities (CAs) to validate identities and code signatures. Adversaries subvert this trust by:
- Installing new root certificates in OS trust stores
- Adding certificates to browser-specific trust stores
- Deploying malicious root CAs via group policy or management tooling
- Modifying cloud or SaaS trust configurations

Once installed, attacker-controlled roots can:
- Validate fraudulent certificates
- Decrypt TLS traffic
- Sign malicious code that appears trusted

Indicators include:
- New or unexpected root certificates
- Certificates without enterprise approval
- Root certificates installed shortly before suspicious activity
- Trust store changes outside maintenance windows

---

## 3. Subtechnique Considerations
Key considerations for T1553.004:
- Requires elevated privileges or administrative access
- Impact spans applications, users, and network traffic
- Detection requires certificate inventory and baselining
- Removal may disrupt legitimate traffic if misattributed

Root certificate abuse provides **systemic trust compromise**.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Installing malicious root CAs to intercept HTTPS traffic
- Using enterprise management tooling to deploy certificates
- Adding root certificates to browser-specific stores
- Leveraging root CAs to sign malware or proxies

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should emphasize **certificate lifecycle and trust-store auditing**:
- Monitor additions and removals of root certificates
- Alert on root CA installation outside approved workflows
- Correlate trust-store changes with suspicious network activity
- Detect new certificates enabling TLS interception

### Data Source Notes
- **Certificate authentication logs**: Identify trust changes
- **Registry and file monitoring**: Track OS trust store modifications
- **Cloud audit logs**: Detect SaaS or cloud CA changes

Common false positives:
- Legitimate enterprise TLS inspection
- Approved PKI rollouts

Tuning guidance:
- Maintain authoritative inventories of trusted roots
- Require approval metadata for certificate deployment

---

## 6. Response Guidance
When suspected:
1. Identify newly installed root certificates
2. Validate certificate origin and approval status
3. Remove unauthorized root certificates
4. Inspect traffic for interception or abuse
5. Rotate credentials and reissue certificates if needed

## 8. SOC Relevance
T1553.004 is critical because:
- Root certificates grant universal trust
- Encrypted traffic visibility may be compromised
- Abuse often persists undetected for long periods

SOC teams must treat **root certificate changes as high-risk events**.

## 11. Malware Usage

## 12. Mitigations
Recommended mitigations:
- Restrict who can install root certificates
- Monitor and audit trust-store changes
- Implement certificate transparency monitoring
- Enforce separation of PKI administration duties

---

## 13. Testing & Validation
Validation approaches:
- Attempt unauthorized root certificate installation in lab
- Validate alerts on trust-store modifications
- Test detection of TLS interception scenarios
- Ensure rapid rollback capability

Include:
- Preconditions: certificate logging enabled
- Required roles/tools: SOC, PKI, endpoint engineering
- Expected outcomes: detection of unauthorized root CAs
- Success criteria: timely alerting and remediation
