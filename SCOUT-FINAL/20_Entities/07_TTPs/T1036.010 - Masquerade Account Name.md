# Masquerading: Masquerade Account Name (T1036.010)

## 1. Summary
Masquerade Account Name describes adversaries **creating, modifying, or abusing user, service, or cloud accounts with names that closely resemble legitimate users or system accounts**. This deception allows malicious activity to blend into normal authentication and account management activity.

Attackers use this technique to:
- Evade identity-based monitoring
- Hide malicious accounts among legitimate users
- Maintain persistence with reduced scrutiny
- Complicate attribution during investigations

---

## 2. Technical Overview
Identity systems often rely on naming conventions and familiarity for trust decisions. Adversaries exploit this by:

- Creating accounts with names similar to administrators or services
- Using typosquatting or subtle character substitutions
- Mimicking vendor, application, or system account names
- Renaming compromised accounts to appear legitimate

This technique applies to:
- Local and domain accounts
- Service and application accounts
- Cloud IAM users and roles
- API and automation identities

Indicators include:
- Accounts with names closely resembling privileged users
- Newly created accounts matching service naming patterns
- Authentication activity from unfamiliar but “normal-looking” accounts
- Privilege usage inconsistent with account age or role

---

## 3. Subtechnique Considerations
Key considerations for T1036.010:
- Strong overlap with **Create Account (T1136)** and **Account Manipulation (T1098)**
- Often paired with **Valid Accounts (T1078)**
- Particularly effective in large or complex identity environments
- Targets human assumptions during identity review

This technique relies on **semantic deception**, not technical exploitation.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Creating accounts with names similar to administrators
- Registering cloud users that resemble service accounts
- Renaming compromised accounts to evade review
- Leveraging masqueraded accounts for routine access

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should focus on **identity anomalies and naming analysis**:
- Detect newly created accounts with suspicious name similarity
- Alert on privilege use shortly after account creation
- Monitor authentication patterns inconsistent with account purpose
- Correlate account creation with intrusion timelines

### Data Source Notes
- **IAM and directory logs**: Detect account creation and modification
- **Authentication logs**: Identify suspicious usage patterns
- **EDR telemetry**: Correlate account usage with endpoint activity

Common false positives:
- Legitimate service accounts
- Enterprise automation users

Tuning guidance:
- Maintain naming standards for service and admin accounts
- Flag accounts violating naming conventions
- Elevate alerts for new privileged accounts

---

## 6. Response Guidance
When suspected:
1. Validate account legitimacy with identity owners
2. Review account creation source and approval context
3. Inspect authentication and privilege usage
4. Disable or restrict malicious accounts
5. Hunt for similarly named accounts

## 8. SOC Relevance
T1036.010 is especially relevant when:
- Suspicious activity appears tied to “normal” accounts
- Privileged access is abused without obvious anomalies
- Identity-based detections are bypassed

SOC teams must analyze **who the account claims to be vs. how it behaves**.

## 12. Mitigations
Recommended mitigations:
- Enforce strict account naming conventions
- Monitor creation of privileged accounts
- Require approvals for identity changes
- Apply least-privilege access controls

---

## 13. Testing & Validation
Validation approaches:
- Create benign test accounts with misleading names
- Validate alerts on naming similarity
- Test SOC workflows for identity masquerading
- Ensure identity reviews consider semantics
