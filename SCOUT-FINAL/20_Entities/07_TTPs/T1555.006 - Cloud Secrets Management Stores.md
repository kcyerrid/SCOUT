## 1. Summary
Cloud Secrets Management Stores (T1555.006) describes adversaries retrieving credential material (passwords, API keys, tokens, encryption keys) from cloud-native secret management services (e.g., AWS Secrets Manager, Azure Key Vault, GCP Secret Manager, HashiCorp Vault) after obtaining sufficient permissions in the cloud environment.

## 2. Technical Overview
Common attacker prerequisites:
- A compromised **cloud identity** (user/service principal/role) with permission to read secrets, or
- Control of a workload/service that can retrieve secrets via API.

Typical behaviors:
- **Secret enumeration and retrieval** via cloud APIs/CLI/SDK (read/list/describe secret calls).
- **Unusual identity usage**: a role/service that normally reads a narrow set of secrets suddenly pulls many secrets or accesses high-sensitivity namespaces.
- **Context anomalies**: secret reads from new regions, IPs, devices, user agents, or outside normal time windows.
- **Chaining**: secret retrieval followed by immediate authentication to other cloud services, lateral movement, persistence changes, or key usage for encryption/decryption operations.

## 3. Subtechnique Considerations
As a subtechnique of **Credentials from Password Stores (T1555)**, this focuses specifically on **cloud-managed secret stores** (distinct from metadata endpoints).
Key nuances for defenders:
- Visibility often depends on **cloud audit logs** and **control-plane telemetry**, not endpoint sensors.
- The highest signal is typically **who/what retrieved which secret**, from where, and how that differs from historical access patterns.
- Secrets can include non-human credentials (API keys, access tokens), making blast radius large and automation fast.

## 4. Procedure Examples
Observed usage examples include:
- [[30_CIPHER/03_Threat_Actors/G0125 - HAFNIUM|G0125]] moving laterally from on-premises environments to steal passwords from Azure Key Vault.
- [[30_CIPHER/05_Malware/S1091 - Pacu|S1091]] retrieving secrets from AWS Secrets Manager (capability documented in tooling).
- [[30_CIPHER/03_Threat_Actors/G1053 - Storm-0501|G1053]] using Azure Key Vault in the context of encryption key storage/operations.

## 5. Detection Guidance
Prioritize detections around **secret retrieval** and **permission abuse**:

1. **High-volume or high-entropy secret reads**
   - Alert on bursts of `GetSecretValue`/`SecretGet`/`vault read`-equivalent activity.
   - Flag retrieval across many secret names/paths in a short period.
2. **Unusual principal accessing secrets**
   - Service/workload identities reading secrets they do not typically access.
   - New principals or newly-permissioned principals reading sensitive secret groups.
3. **Anomalous access context**
   - New source IP ranges, geographies/regions, user agents, or automation frameworks.
   - Access outside standard maintenance windows.
4. **Precursor signals**
   - IAM/role policy changes granting secret access followed closely by secret reads.
   - Credential/token theft indicators preceding secret reads.

### 5.1. Data Source Notes
Telemetry to collect and correlate:
- **Cloud control-plane audit logs** for secret manager APIs (read/list/describe) and IAM changes.
- **Identity telemetry**: sign-in logs, role assumption, token issuance/refresh events.
- **Network context**: source IP/ASN, region, device posture (where available).
- **Workload telemetry** (if using Vault or self-hosted secrets tooling): auth method logs, lease/token creation, audit devices.

## 6. Response Guidance
1. **Immediate containment**
   - Revoke sessions/tokens and rotate affected secrets (prioritize privileged service credentials and long-lived keys).
   - Remove unauthorized secret-read permissions and investigate recent IAM changes.
2. **Scope and impact**
   - Determine which secrets were accessed and whether they enable access to other systems (CI/CD, databases, IdP, SaaS).
   - Hunt for follow-on usage (new logins, API calls) using rotated secrets.
3. **Hardening**
   - Enforce least privilege on secret read permissions and segment secrets by environment/team.
   - Require strong authentication controls (MFA where applicable) and limit role assumption paths.

## 8. SOC Relevance
- **Critical blast radius**: a single secrets-store compromise can unlock multiple downstream systems.
- **Strong cloud-native detection opportunities**: secret retrieval is a discrete, loggable event in many providers.
- **Actionable response**: rotate secrets and revoke access quickly to cut off attacker momentum.

## 12. Mitigations
- **M1026 - Privileged Account Management**: strictly limit which accounts/services can query secret managers; scope access to only required secrets.

## 13. Testing & Validation
- Validate detections with controlled testing in a non-production cloud account:
  - Generate known-good secret retrievals from approved identities, then compare to test retrievals from atypical identities/locations to confirm alerting.
