# Masquerading: Overwrite Process Arguments (T1036.011)

## 1. Summary
Overwrite Process Arguments describes adversaries **modifying the in-memory command-line arguments of a running process** so that monitoring tools, system utilities, and analysts see benign or misleading process information instead of the true execution parameters.

Attackers use this technique to:
- Hide malicious intent from process listings
- Evade command-line–based detections
- Mislead analysts during live response
- Reduce forensic clarity of execution activity

---

## 2. Technical Overview
On Unix-like systems, process arguments are typically stored in memory regions that can be modified after process startup. Adversaries exploit this behavior by:

- Overwriting `argv` values after execution
- Using native APIs or direct memory manipulation
- Replacing malicious arguments with benign placeholders
- Masking sensitive parameters such as C2 addresses or script paths

Key characteristics:
- Process behavior does not match displayed arguments
- Command-line inspection tools show misleading values
- Memory-level discrepancies between execution and display
- Execution artifacts hidden from routine inspection

Indicators include:
- Processes whose behavior conflicts with visible arguments
- Command lines that appear generic or empty
- Memory artifacts inconsistent with process listings
- Suspicious activity lacking corresponding command context

---

## 3. Subtechnique Considerations
Key considerations for T1036.011:
- Most applicable to Linux and macOS environments
- Strong overlap with **Command and Scripting Interpreter (T1059)**
- Often paired with **Native API Execution (T1106)**
- Complements **Indicator Removal on Host (T1070)**

This technique targets **runtime visibility**, not execution mechanics.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Launching a process with malicious arguments
- Overwriting arguments immediately after startup
- Replacing command-line text with benign strings
- Hiding sensitive parameters from monitoring tools

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should emphasize **behavioral and memory-based analysis**:
- Detect processes performing actions inconsistent with arguments
- Monitor API calls that modify process memory
- Compare runtime behavior with expected command-line usage
- Use EDR features that capture initial execution parameters

### Data Source Notes
- **Process creation telemetry**: Capture original arguments
- **Memory analysis**: Identify overwritten argument regions
- **EDR telemetry**: Correlate execution behavior with lineage

Common false positives:
- Legitimate daemons that sanitize arguments
- Security or privacy-focused applications

Tuning guidance:
- Baseline expected argument patterns for services
- Elevate alerts when argument discrepancies align with suspicious behavior

---

## 6. Response Guidance
When suspected:
1. Capture volatile memory if possible
2. Review initial execution telemetry
3. Analyze process behavior and network activity
4. Isolate affected systems if malicious activity is confirmed
5. Hunt for similar argument-masking behavior

## 8. SOC Relevance
T1036.011 is especially relevant when:
- Command-line data appears incomplete or misleading
- Behavioral detections fire without visible context
- Analysts suspect tampering with process visibility

SOC teams should rely on **initial execution telemetry and behavior**, not live arguments alone.

## 12. Mitigations
Recommended mitigations:
- Capture command-line arguments at process start
- Monitor memory modification APIs
- Use EDR tools with runtime integrity checks
- Correlate execution with behavior and network activity

- Validate alerts on argument discrepancies
- Test SOC workflows for runtime masquerading
- Ensure visibility into original execution context
