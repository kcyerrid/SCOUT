# Obfuscated Files or Information: Junk Code Insertion (T1027.016)

## 1. Summary
Junk Code Insertion describes adversaries **adding non-functional or irrelevant code into malicious payloads** to increase complexity, disrupt static analysis, and evade signature-based detection. The inserted code does not affect the malware’s core functionality but significantly increases noise for analysts and automated tools.

Adversaries use this technique to:
- Inflate code size and complexity
- Break static signatures and heuristics
- Obscure true execution paths
- Delay reverse engineering efforts

---

## 2. Technical Overview
Junk code may be inserted at:
- Compile time via automated mutation engines
- Post-compilation using binary rewriting
- Runtime through dynamically generated instructions

Common junk code patterns include:
- No-op instructions
- Dead code branches
- Redundant loops or calculations
- Unused functions or variables

Indicators include:
- Large volumes of unreachable code
- High instruction entropy without functional gain
- Consistent behavior despite structural variance
- Execution paths that bypass large code sections

---

## 3. Subtechnique Considerations
Key considerations for T1027.016:
- Often paired with **Polymorphic Code (T1027.014)**
- May coexist with **Software Packing (T1027.002)**
- Junk code increases analyst workload, not capability
- Behavioral analysis remains effective

Junk code insertion targets **analysis efficiency**, not execution concealment.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Injecting dead branches throughout malware
- Randomizing non-functional instruction sequences
- Padding binaries with meaningless operations
- Auto-generating junk code during build processes

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should emphasize **runtime behavior over structural complexity**:
- Identify consistent execution paths across variants
- Detect excessive unreachable code regions
- Focus on functional behavior despite code inflation
- Use dynamic analysis and emulation

### Data Source Notes
- **Malware analysis**: Identify dead code and no-op patterns
- **EDR telemetry**: Observe consistent runtime behavior
- **Memory analysis**: Reveal actual execution paths

Common false positives:
- Legitimate obfuscated or protected software
- Compiler-optimized binaries

Tuning guidance:
- Baseline known protected applications
- Elevate alerts when junk-heavy binaries exhibit malicious behavior

---

## 6. Response Guidance
When suspected:
1. Analyze runtime execution paths
2. Ignore non-functional code regions
3. Extract meaningful logic via dynamic analysis
4. Hunt for behavioral indicators across variants
5. Update detections to focus on behavior

## 8. SOC Relevance
T1027.016 is relevant because:
- Static complexity does not equal capability
- Analysts may be distracted by noise
- Detection must focus on execution behavior

SOC teams should prioritize **behavioral correlation over static code metrics**.
