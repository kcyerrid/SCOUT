# T1547.005 – Security Support Provider

## 1. Technique Overview
**Security Support Provider (T1547.005)** is a sub-technique of **Boot or Logon Autostart Execution (T1547)** in MITRE ATT&CK v18. Adversaries abuse **Security Support Providers (SSPs)**—DLLs loaded by the Local Security Authority Subsystem Service (LSASS)—to execute malicious code during authentication operations.

Because SSPs are part of Windows’ core security infrastructure, malicious SSPs are executed with **SYSTEM-level privileges**, making this technique highly stealthy and impactful.

## 2. Adversary Objectives
Adversaries use this technique to:
- Achieve persistent execution during authentication events
- Run code within the LSASS process
- Intercept, log, or manipulate authentication credentials
- Maintain stealthy, high-privilege access

## 3. Common Abuse Patterns
- Registering malicious SSP DLLs via:
  - `HKLM\SYSTEM\CurrentControlSet\Control\Lsa\Security Packages`
- Modifying existing SSP entries to include attacker-controlled DLLs
- Deploying credential-logging SSPs
- Masquerading malicious DLLs as legitimate security components
- Combining SSP abuse with credential access techniques

## 4. Detection Considerations
Detection requires **advanced monitoring of security-sensitive components**, including:
- Monitoring changes to LSA SSP registry keys
- Detecting new or unsigned DLLs loaded by LSASS
- Alerting on authentication package or SSP modifications
- Correlating SSP changes with credential access anomalies
- Reviewing memory-resident modules within LSASS

## 5. Defensive Mitigations
- Restrict administrative access to LSA configuration keys
- Enable LSASS protection (RunAsPPL) where supported
- Enforce code signing requirements for SSP DLLs
- Monitor and audit authentication-related registry keys
- Treat unauthorized SSP changes as critical security events

## 6. Operational Impact
If successful, T1547.005 can:
- Provide long-term, stealthy persistence
- Enable SYSTEM-level code execution
- Facilitate credential harvesting
- Severely undermine trust in authentication processes

## 7. Analyst Notes
SSP abuse is a classic but still dangerous persistence technique. Because SSPs load early and operate within LSASS, remediation often requires **offline forensic analysis** or full system rebuilds. Any unexplained SSP modification should be considered a strong indicator of deep compromise.
