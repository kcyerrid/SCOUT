## 1. Summary
Application Access Token (T1550.001) is adversary authentication to remote services using stolen or replayed application access tokens (e.g., OAuth/SAML/JWT, cloud federation/session tokens) to bypass interactive authentication (including MFA) and access APIs/data as a user or service principal.

## 2. Technical Overview
- **What it looks like:** API access and sign-ins where the “credential” is a token (access/refresh/session/federation) rather than a password.
- **Common token abuse patterns**
  - OAuth access/refresh token replay from new devices/locations.
  - Cloud federation/session tokens minted via STS/IAM calls inconsistent with baseline.
  - Service principal/service account token reuse across workloads (especially in containers).
- **Why it matters:** Token use often resembles legitimate automation; detection depends heavily on **context**, **issuance chain**, and **policy expectations**.

## 3. Subtechnique Considerations
- This is a sub-technique of [[20_Entities/07_TTPs/TA0005 - Defense Evasion/T1550 - Use Alternate Authentication Material|T1550]].
- Compared to other T1550 sub-techniques, T1550.001 is **cloud/IdP heavy** and typically detected via **IdP/SaaS audit trails** and **API telemetry**, not endpoint-only logs.

## 4. Procedure Examples
Documented examples include:
- **APT28:** Abused OAuth access tokens via malicious applications for email account access.
- **CreepyDrive:** Uses legitimate OAuth refresh tokens to authenticate with OneDrive.
- **HAFNIUM:** Abused service principals with administrative permissions for data access/exfiltration.
- **Peirates:** Uses stolen service account tokens; supports switching between valid service accounts.
- **SolarWinds Compromise:** Use of compromised service principals to alter Office 365 environment. :contentReference[oaicite:16]{index=16}

## 5. Detection Guidance
Focus on **token issuance + token use** correlation and enforcement of “expected context.”

**High-signal detections**
- **Token use without expected authentication context**
  - Access token usage without preceding interactive login/MFA challenge.
  - Refresh token reuse far beyond normal lifecycle patterns.
- **Abnormal token minting**
  - STS/IAM federation/token requests from unusual principals, regions, or roles.
  - Tokens requested “on behalf of” other accounts where this is not standard practice.
- **Suspicious scopes/permissions**
  - New or elevated OAuth scopes, delegated permission grants, or service principal role changes preceding access.
- **Cross-environment drift**
  - Token created in one context (region/device/workload) but used in another, especially across workloads/containers.

MITRE detection strategy highlights core telemetry:
- **Web Credential Usage (DC0007):** Token issuance/usage and API access (e.g., CloudTrail AssumeRole/GetFederationToken; IdP sign-in logs token events; M365 unified audit). :contentReference[oaicite:17]{index=17}

## 6. Response Guidance
1. **Revoke tokens/sessions**
   - Invalidate refresh tokens, session tokens, and related grants (IdP/SaaS).
2. **Contain affected principals**
   - Disable/suspend impacted users/apps/service principals; rotate secrets/certs used for token signing or client auth.
3. **Scope blast radius**
   - Enumerate all resources accessed by the token (API logs, audit trails) within the suspected window.
4. **Remediate root cause**
   - Remove malicious apps/consents, fix misconfigured federation/role assumption paths, tighten conditional access.
5. **Enforce stronger controls**
   - Device binding / proof-of-possession where available; reduce token lifetimes; restrict admin consent and app allowlists.

## 8. SOC Relevance
- **Detection engineering priority:** High in cloud-first orgs; often a precursor to mailbox access, data collection, and SaaS lateral movement.
- **Key SOC dependencies:** IdP + SaaS audit ingestion, strong identity enrichment (device, geo, app ID), and automated token revocation playbooks.
- **Primary failure mode:** Treating “successful OAuth/API calls” as benign without verifying issuance context and policy compliance.

## 12. Mitigations
- **Account Use Policies:** Restrict token use to expected networks/contexts; apply data perimeters where possible. :contentReference[oaicite:22]{index=22}
- **Application Developer Guidance:** Token binding / proof-of-possession to reduce replay value. :contentReference[oaicite:23]{index=23}
- **Audit:** Review cloud/container accounts, permissions, and ability to request tokens on behalf of others; monitor OAuth actions. :contentReference[oaicite:24]{index=24}
- **Restrict Web-Based Content:** Restrict/allowlist third-party apps; block end-user consent where appropriate. :contentReference[oaicite:25]{index=25}
