## 1. Summary
Socket Filters (T1205.002) attach packet filters to sockets/interfaces (e.g., via `libpcap`/WinPcap/Npcap or OS socket filter APIs) so a backdoor stays dormant until a crafted packet matches the filter. This enables stealthy activation of persistence or command-and-control behaviors with minimal on-host activity until triggered.

## 2. Technical Overview
- **Core behavior:** a process installs/uses packet-capture or raw-socket capability and sets a filter (e.g., BPF/eBPF, pcap filters, Windows capture stack).
- **Trigger:** low-volume inbound packet(s) matching filter criteria (token/byte pattern, protocol/port/ICMP characteristics).
- **Response:** actions such as:
  - Activating a reverse shell or outbound beacon
  - Installing/activating additional implant functionality
  - Performing a “ping back” or command processing routine
- **Why it’s stealthy:**
  - No open listening port required.
  - Low CPU overhead.
  - Visibility gaps in raw socket and capture-stack usage, especially on non-EDR-covered hosts.

## 3. Subtechnique Considerations
- This is a sub-technique of **Traffic Signaling (T1205)**.
- Compared to **Port Knocking (T1205.001)**:
  - Network signatures may be fewer (often a single trigger packet).
  - Host artifacts (capture drivers, module loads, raw socket calls) become more important.

## 4. Procedure Examples
ATT&CK documents, among others:
- [[30_CIPHER/05_Malware/S1161 - BPFDoor|BPFDoor]] attaching BPF bytecode to view packets on common ports and forking on “magic bytes.”
- [[30_CIPHER/05_Malware/S1224 - CASTLETAP|CASTLETAP]] listening for specialized ICMP activation on compromised network devices.
- [[30_CIPHER/05_Malware/S0587 - Penquin|Penquin]] installing TCP/UDP filters on an interface.
- [[30_CIPHER/05_Malware/S1123 - PITSTOP|PITSTOP]] evaluating incoming commands over a socket for predefined magic bytes and duplicating the socket for further comms.

## 5. Detection Guidance
**Primary detection goal:** identify capture/raw-socket capability + trigger packet + follow-on outbound connection or execution.

**Host detections (high-signal):**
- **Capture stack installation/usage:**
  - Windows: creation of capture-related services/drivers (e.g., Npcap), driver loads, and module loads consistent with packet capture libraries.
  - Linux/macOS: raw socket activity, BPF program loads, or access to `/dev/bpf*` where applicable.
- **Suspicious process context:**
  - Non-standard binaries loading capture libraries or requesting raw socket privileges.
  - Unusual persistence context (daemon/service not in baseline).
- **Trigger-to-egress correlation:**
  - Matching inbound packet observed (via NSM) followed by outbound connection from the process that loaded capture components.

**Network detections:**
- **Low-volume trigger traffic**:
  - Single inbound packet to uncommon destination port/protocol or with unusual flags/content.
  - Followed by outbound connection to the trigger origin or a new C2 endpoint.

**Tuning guidance:**
- Maintain allowlists for legitimate capture tooling and expected installers (IT tooling, EDR drivers, sanctioned Npcap deployments).
- Establish baselines of packet-capture library usage by host role (servers rarely need it).

### 5.1. Data Source Notes
- **Service Creation / Driver Load / Module Load:** Critical on Windows to spot capture driver installs/loads and library usage.
- **Process Creation:** Correlate which process is responsible for capture capability and subsequent connections.
- **Network Traffic Content:** Needed to spot the trigger packet (when inspection is permissible).
- **Network Connection Creation:** Needed to link trigger to follow-on outbound sessions.

## 6. Response Guidance
1. **Contain**
   - Isolate impacted hosts; block observed trigger sources/destinations.
2. **Triage**
   - Identify installed/loaded capture drivers/modules and the owning process/service.
   - Determine persistence mechanism (service entry, launch agent, cron/systemd unit).
3. **Eradicate**
   - Remove unauthorized drivers/modules, services, and binaries; revoke elevated capabilities (e.g., raw socket caps).
4. **Recover**
   - Restore clean baseline configurations and validate network protections.
5. **Harden**
   - Restrict packet-capture tooling installation and raw socket permissions.
   - Add detections for unexpected capture stack usage on servers and endpoints.

- High relevance for Linux and appliance backdoors where capture/raw socket triggers provide stealth.
- Watch for **unexpected capture tooling** on servers and **single-packet triggers** tied to rapid outbound connections.

## 12. Mitigations
- **Filter Network Traffic:** Use stateful firewalling/segmentation and restrict inbound paths that could deliver trigger packets; apply tight ingress controls to sensitive hosts.

## 13. Testing & Validation
- Validate with authorized lab testing:
  - Deploy a benign capture library/service in a controlled environment and confirm visibility into service/driver/module events.
  - Generate a controlled “trigger packet” and ensure correlation to subsequent outbound connection is detected.
  - Validate allowlists for legitimate capture tools to prevent excessive false positives.

## 15. Notes
- Socket filters are easiest to catch by correlating **capture stack usage** with **rare inbound triggers** and **fast outbound follow-on**.
- Prioritize server baselines: most server roles should not install packet-capture drivers or load capture libraries outside approved tooling.
