# Component Object Model (T1559.001)

## 1. Summary
Component Object Model (COM) describes adversary abuse of Microsoft’s COM/DCOM framework to execute code within the context of another process or system service. COM enables inter-process communication and object invocation, which adversaries exploit to trigger execution paths without directly launching new binaries.

This subtechnique is commonly associated with stealthy execution, lateral movement, and privilege escalation in Windows environments.

---

## 2. Technical Overview
COM provides a mechanism for software components to expose objects and methods that can be invoked locally or remotely (DCOM).

Adversaries abuse COM by:
- Instantiating malicious or hijacked COM objects
- Invoking exposed methods that execute commands
- Abusing DCOM for remote execution
- Leveraging existing system COM classes to evade detection

Artifacts include COM object instantiation events, registry access to CLSIDs, process execution initiated indirectly, and authentication or network activity for DCOM usage.

---

## 3. Subtechnique Considerations
T1559.001 is a Windows-specific IPC mechanism and differs from other IPC subtechniques by relying on registered COM classes.

Key considerations include:
- COM object abuse often leaves minimal process creation artifacts
- Registry-based persistence and execution overlap
- Legitimate enterprise software heavily uses COM/DCOM

Detection must distinguish malicious COM usage from normal system behavior.

---

## 4. Procedure Examples
Observed adversary procedures include:
- Using `wmic` or custom tooling to invoke COM objects
- Abusing Office COM objects for execution
- Leveraging DCOM for remote command execution
- Hijacking COM registrations to redirect execution

Analysts may observe registry access to suspicious CLSIDs followed by execution.

---

## 5. Detection Guidance
Detection should focus on:
- Unusual COM object instantiation by non-standard processes
- COM usage followed by command execution or network activity
- Registry modifications to COM-related keys
- DCOM authentication from unexpected sources

Correlation between registry, process, and authentication telemetry improves detection fidelity.

### Data Source Notes
- **Registry:** Critical for identifying CLSID abuse
- **Process Execution:** Provides indirect execution context
- **Authentication Logs:** Useful for DCOM-based remote execution

---

## 6. Response Guidance
When malicious COM activity is suspected:
- Identify abused CLSIDs and associated binaries
- Review registry modifications related to COM objects
- Isolate affected systems if remote execution is involved
- Assess for persistence mechanisms leveraging COM

Preserve registry hives, execution telemetry, and authentication logs for investigation.

## 8. SOC Relevance
COM abuse is difficult to detect due to its prevalence in legitimate Windows operations. SOC teams require registry visibility and behavioral analytics to identify anomalous COM execution patterns.

---

## 9. Threat Actor Usage
This subtechnique is used by:
- Advanced persistent threat groups
- Sophisticated ransomware operators
- Malware frameworks leveraging living-off-the-land techniques

Confidence in targeted but high-impact usage is high.

---

## 10. Campaign Usage
COM-based execution has appeared in:
- Lateral movement phases of enterprise intrusions
- Stealthy post-exploitation campaigns
- Long-dwell Windows environment compromises

## 12. Mitigations
Effective mitigations include:
- Monitoring and hardening COM/DCOM configurations
- Restricting unnecessary DCOM access
- Enforcing least-privilege execution
- Deploying EDR with COM visibility
- Auditing COM-related registry changes

---

## 13. Testing & Validation
Validation approaches include:
- Atomic Red Team tests for COM execution
- Purple team simulations of DCOM-based lateral movement
- Review of alerts tied to suspicious COM object usage

Successful validation results in detection of unauthorized COM-based execution.
