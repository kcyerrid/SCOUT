# Impair Defenses: Disable or Modify Cloud Logs (T1562.008)

## 1. Summary
Disable or Modify Cloud Logs describes adversaries **disabling or altering cloud logging capabilities and integrations** to limit data collection on their actions and evade detection. Cloud audit and application logs are frequently the primary (and sometimes only) forensic record of cloud activity; impairing them meaningfully degrades detection, investigation, and attribution. :contentReference[oaicite:0]{index=0}

---

## 2. Technical Overview
Cloud platforms and SaaS services provide logging through native audit pipelines and optional integrations (e.g., exporting to SIEM, object storage, or event streaming). Adversaries with sufficient permissions may impair logging by: disabling log sources, modifying log sinks/destinations, reducing retention, changing encryption/validation settings, or severing downstream integrations. :contentReference[oaicite:1]{index=1}

Common examples include:
- **AWS**: Disabling CloudTrail/CloudWatch integrations; removing associated notification topics; disabling multi-region logging; altering log file validation/encryption settings. :contentReference[oaicite:2]{index=2}
- **Microsoft 365**: Disabling or bypassing mailbox auditing and/or reducing audit coverage by changing licensing/auditing configuration. :contentReference[oaicite:3]{index=3}

Typical artifacts and indicators:
- Logging service disable/modify events in audit logs
- Sudden drops in log ingestion volume
- Changes to log export destinations, retention, or coverage
- Elevated identity activity correlating with logging changes

---

## 3. Subtechnique Considerations
Key considerations for T1562.008:
- Often follows **cloud identity compromise** or privileged role acquisition (e.g., administrative roles).
- Frequently paired with **other defense impairment** activities (e.g., cloud security control changes, firewall changes, or account manipulation) to create a detection blind spot. :contentReference[oaicite:4]{index=4}
- High confidence indicator of malicious intent when performed outside of approved change windows.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Disabling tenant audit logging or specific audit sub-feeds for targeted users/services
- Removing log export/sink destinations to prevent SIEM ingestion
- Shortening retention or disabling multi-region/organization logging
- Disabling validation/encryption features that support forensic integrity

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should focus on **logging integrity and configuration drift**:
- Alert on API calls that disable or modify logging/log exports/sinks
- Detect changes to retention, scope, destinations, validation, and encryption controls
- Monitor ingestion health (sudden silence from a log source is a signal)
- Correlate logging changes with risky identity events (new roles, unusual admin actions)

### Data Source Notes
- **Cloud audit logs**: Primary source for who/what changed logging. :contentReference[oaicite:5]{index=5}
- **SIEM ingestion metrics**: Detect silent failures and volume drops.
- **Identity provider logs**: Correlate privilege changes with logging impairment.
- **Email/Office audit logs**: Detect mailbox audit bypass/disablement behavior. :contentReference[oaicite:6]{index=6}

Common false positives:
- Planned onboarding/offboarding of log sinks
- Tenant reconfiguration or license changes
- Testing in non-production environments

Tuning guidance:
- Require change tickets/approvals for audit/log pipeline modifications
- Baseline normal ingestion volumes per service and tenant
- Add “break-glass” alerts for disabling high-value logs (e.g., org audit, admin audit)

---

## 6. Response Guidance
When activity is suspected:
1. **Restore logging immediately** (re-enable sources, sinks, retention, validation/encryption).
2. **Preserve remaining logs** and export configuration state (IaC templates, audit snapshots).
3. **Review identity activity** around the change (role grants, token creation, suspicious sign-ins).
4. **Hunt for actions taken during the logging gap** (resource creation, access, exfiltration).
5. **Rotate credentials and revoke sessions/tokens** for accounts involved; review conditional access.
6. Escalate if logging was impaired on high-value tenants or security tools.

## 8. SOC Relevance
T1562.008 is one of the **highest-severity techniques in cloud/SaaS** because it directly undermines the SOC’s ability to detect and reconstruct attacker activity. Logging impairment should be treated as an **incident condition** until proven otherwise. :contentReference[oaicite:7]{index=7}

---

## 9. Threat Actor Usage
This technique is commonly observed in cloud-focused intrusions and is used by multiple actors to reduce visibility prior to:
- Data theft and mailbox collection
- Persistence establishment
- Lateral movement across cloud resources

MITRE includes procedure examples (e.g., APT29 activity in Microsoft 365) demonstrating this pattern. :contentReference[oaicite:8]{index=8}

---

## 10. Campaign Usage
Frequently observed in:
- Cloud account takeover campaigns
- SaaS tenant compromise operations
- Post-compromise phases where attackers expect SOC monitoring

---

## 11. Malware Usage
Associated with:
- Cloud post-exploitation frameworks and automation tooling
- Scripts abusing cloud provider APIs
- Operator-driven intrusions leveraging compromised credentials rather than on-host malware

---

## 12. Mitigations
Recommended mitigations:
- Enforce least privilege for logging administration roles
- Require MFA and conditional access for privileged accounts
- Use immutable / write-once log storage and separate security accounts for log custody
- Enable org-wide, multi-region logging with validation/encryption where supported
- Monitor and alert on any logging disablement or sink modification events

---

## 13. Testing & Validation
Validation approaches:
- Simulate controlled changes to logging settings in a test tenant
- Validate alerting on log disablement, sink deletion, and retention reduction
- Test SOC playbooks for “log gap” response, including configuration rollback
- Verify that ingestion monitoring detects silent loss of log sources
