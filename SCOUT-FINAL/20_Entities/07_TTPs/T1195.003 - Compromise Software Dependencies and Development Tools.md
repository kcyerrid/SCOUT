# Compromise Software Dependencies and Development Tools (T1195.003)

## 1. Summary
Compromise Software Dependencies and Development Tools describes adversary manipulation of third-party libraries, open-source dependencies, build tools, or developer environments to introduce malicious code into downstream software. By targeting dependencies and tooling rather than end products, adversaries exploit implicit trust within modern software development ecosystems.

This subtechnique enables scalable and stealthy initial access across multiple downstream organizations.

---

## 2. Technical Overview
Adversaries compromise software dependencies and development tools by:
- Publishing malicious or trojanized packages to public repositories
- Hijacking legitimate dependency names (typosquatting or namespace confusion)
- Compromising developer workstations or build tools
- Injecting malicious code into CI/CD tooling or plugins

Artifacts may include unexpected dependency changes, anomalous build behavior, unauthorized repository access, and suspicious network connections during build or execution.

---

## 3. Subtechnique Considerations
T1195.003 focuses on **dependencies and tooling**, distinguishing it from:
- Compromised vendor-distributed software
- Hardware or firmware tampering

Detection is complicated by the dynamic and decentralized nature of dependency management and open-source ecosystems.

---

## 4. Procedure Examples
Observed adversary procedures include:
- Publishing malicious packages with names similar to popular libraries
- Injecting backdoors into build scripts or CI/CD plugins
- Compromising developer environments to alter source code or dependencies
- Abusing package update mechanisms to propagate malicious changes

Analysts may observe malicious behavior originating from newly introduced or updated dependencies.

---

## 5. Detection Guidance
Detection should emphasize supply chain visibility and integrity monitoring:
- Monitoring dependency changes and package versions
- Detecting anomalous build or pipeline behavior
- Identifying suspicious network activity during build processes
- Auditing access to code repositories and developer tools

Behavioral analysis and dependency auditing are critical for effective detection.

### Data Source Notes
- **Package Manager Logs:** High value for identifying unexpected dependency changes
- **CI/CD Logs:** Critical for detecting build pipeline manipulation
- **Code Repository Logs:** Essential for identifying unauthorized commits or access

---

## 6. Response Guidance
When dependency or tooling compromise is suspected:
- Immediately halt builds and deployments
- Identify affected packages, versions, and downstream consumers
- Remove malicious dependencies and rotate credentials
- Coordinate remediation with developers and security teams

Preserve build logs, dependency manifests, and affected artifacts for analysis.

## 8. SOC Relevance
Dependency and tooling compromise is increasingly common due to the widespread use of open-source components and automated build systems. SOC teams often lack visibility into development pipelines, making collaboration with engineering teams essential.

---

## 9. Threat Actor Usage
This subtechnique has been used by:
- Nation-state actors targeting software ecosystems
- Cybercriminal groups seeking scalable access
- Advanced actors abusing open-source trust models

Confidence in continued growth of this technique is high.

---

## 10. Campaign Usage
Compromise of dependencies and development tools has appeared in:
- Open-source ecosystem poisoning campaigns
- Targeted intrusions against software vendors
- Long-term supply chain access operations

---

## 11. Malware Usage
Malware delivered via compromised dependencies or tooling often appears as:
- Trojans embedded in legitimate libraries
- Backdoored build artifacts
- Loaders or beacons introduced during build time

Post-compromise tooling may later include:
- [[30_CIPHER/05_Malware/S0154 - Cobalt Strike|Cobalt Strike]]

---

## 12. Mitigations
Effective mitigations include:
- Dependency pinning and integrity verification
- Software composition analysis (SCA)
- Securing developer environments and credentials
- Hardening CI/CD pipelines
- Monitoring build-time network activity

---

## 13. Testing & Validation
Validation approaches include:
- Red team simulations of malicious dependency introduction
- CI/CD integrity and access control testing
- Purple team exercises focused on build pipeline abuse

Successful validation identifies unauthorized dependency or tooling changes.
