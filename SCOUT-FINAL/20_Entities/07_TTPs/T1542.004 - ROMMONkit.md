# Pre-OS Boot: ROMMONkit (T1542.004)

## 1. Summary
ROMMONkit describes adversaries **modifying ROM Monitor (ROMMON) firmware on network devices**—such as routers, switches, or other embedded network infrastructure—to gain persistent, pre-operating-system control. ROMMON executes before the device’s primary operating system, enabling stealthy persistence that is highly resistant to detection and remediation.

Adversaries use this technique to:
- Establish durable persistence on network infrastructure
- Execute malicious logic before network OS initialization
- Bypass network OS-level security and logging
- Maintain access across device reboots and OS reinstalls

---

## 2. Technical Overview
ROMMON is a low-level boot and recovery environment used by many network devices. Adversaries may abuse it by:
- Replacing or modifying ROMMON firmware images
- Altering boot variables to load attacker-controlled images
- Injecting malicious logic into ROMMON routines
- Exploiting vulnerabilities in firmware update or recovery processes

Common targets include:
- Enterprise routers and switches
- Embedded network appliances
- Devices supporting remote ROMMON access or recovery modes

Indicators include:
- Unexpected ROMMON version or checksum changes
- Altered boot behavior or recovery prompts
- Network traffic originating before full OS initialization
- Persistence that survives OS reflashing

---

## 3. Subtechnique Considerations
Key considerations for T1542.004:
- Network-device–specific and highly specialized
- Often requires physical access, supply-chain compromise, or privileged credentials
- Detection tooling is limited compared to endpoint systems
- Remediation may require hardware replacement or vendor intervention

ROMMON compromise operates **below the network operating system trust boundary**.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Modifying ROMMON to redirect boot execution
- Installing malicious pre-OS network listeners
- Altering recovery logic to reinstate attacker firmware
- Using ROMMON persistence to reload malicious OS images

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should emphasize **firmware integrity and anomalous device behavior**:
- Validate ROMMON firmware versions and hashes
- Monitor boot variables and recovery configurations
- Detect unexplained device behavior during boot
- Correlate persistence across OS reinstallation events

### Data Source Notes
- **Firmware integrity monitoring**: Primary detection mechanism
- **Network device logs**: Capture boot and recovery events
- **Configuration management logs**: Track unauthorized changes

Common false positives:
- Legitimate firmware recovery or upgrades
- Vendor maintenance actions

Tuning guidance:
- Maintain authoritative firmware baselines
- Require change control for ROMMON-related actions

---

## 6. Response Guidance
When suspected:
1. Isolate the affected network device immediately
2. Validate ROMMON firmware against vendor baselines
3. Reflash firmware using trusted vendor procedures
4. Replace hardware if integrity cannot be assured
5. Investigate supply-chain and administrative access exposure

## 8. SOC Relevance
T1542.004 is critical because:
- Network infrastructure compromise impacts entire environments
- Endpoint tools provide no visibility
- Recovery is complex and disruptive

SOC teams must treat **network firmware compromise as a crisis-level event**.

## 11. Malware Usage

## 12. Mitigations
Recommended mitigations:
- Restrict ROMMON access and authentication
- Monitor firmware integrity continuously
- Apply strict change management to network devices
- Validate firmware authenticity during procurement

---

## 13. Testing & Validation
Validation approaches:
- Inventory and baseline ROMMON firmware
- Test alerting on unauthorized firmware changes
- Conduct tabletop exercises for network firmware compromise
- Validate vendor recovery and reflash procedures

Include:
- Preconditions: firmware baselines established
- Required roles/tools: network engineering, DFIR, vendor support
- Expected outcomes: detection of unauthorized ROMMON changes
- Success criteria: restoration of trusted firmware state
