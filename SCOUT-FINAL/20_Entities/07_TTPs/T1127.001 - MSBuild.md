## 1. Summary
Adversaries may abuse **MSBuild.exe** (Microsoft Build Engine) to compile and execute attacker-controlled code embedded in project files, leveraging a signed Microsoft binary to bypass application control policies. Detection is most effective using behavior-chain correlation around **msbuild.exe execution + suspicious children + artifact creation + egress** outside normal developer/build contexts.

## 2. Technical Overview
MSBuild is a legitimate build platform often installed with Visual Studio/.NET tooling. Abuse commonly involves:
- Executing project files that contain attacker logic (e.g., inline tasks embedded in XML).
- Using msbuild.exe as a trusted parent process to launch additional tooling or stage payloads.
- Blending into environments where .NET tooling exists, or placing MSBuild binaries in unexpected paths.

Defender-relevant behaviors:
- `msbuild.exe` on **non-dev** endpoints or outside normal build schedules.
- Anomalous command lines (remote shares, unusual paths, obfuscated properties).
- Short-window follow-on:
  - LOLBin/script interpreter child processes
  - file writes to user-writable paths followed by execution
  - unsigned module loads
  - outbound network connections

## 3. Subtechnique Considerations
- MSBuild abuse can be noisy on build servers; strong **asset role classification** (dev/build vs user endpoints) is critical.
- Tighten rules by requiring **multiple chained behaviors** (e.g., msbuild + file write + egress) rather than msbuild alone.

## 4. Procedure Examples
MITRE ATT&CK lists the following procedure examples:
- [[30_CIPHER/05_Malware/S0363 - Empire|Empire]]: uses modules that can abuse trusted utilities like MSBuild.exe.
- C0001 - Frankenstein: used MSBuild to execute an actor-created file.
- [[30_CIPHER/05_Malware/S0013 - PlugX|PlugX]]: variants have loaded as shellcode within a .NET Framework project via msbuild.exe to bypass application controls.

## 5. Detection Guidance
Recommended detection is **correlation-based**:

- **Context validation**
  - Flag msbuild.exe on endpoints not in developer/build allowlists.
  - Alert on msbuild.exe launched by uncommon parents (Office, browsers, archive tools, user shells).

- **Command-line and path anomalies**
  - Non-canonical msbuild paths, execution from user-writable directories, or project files located in `%TEMP%/%APPDATA%/Downloads` or remote shares.

- **Behavior-chain correlation**
  - msbuild.exe followed by:
    - high-risk children (powershell.exe, cmd.exe, rundll32.exe, regsvr32.exe, wscript.exe, mshta.exe)
    - file creation then execution
    - suspicious module loads (unsigned/user-writable)
    - memory injection / process access patterns
    - rapid outbound network connections

## 6. Response Guidance
1. **Initial triage**
   - Capture msbuild.exe command line, parent process, user, and host role.
   - Identify referenced project/target files (location, hash, signer, first-seen time).

2. **Contain**
   - Isolate host if chaining indicates execution + network egress.
   - Block msbuild.exe on non-dev endpoints via WDAC/AppLocker (or scoped EDR rules).

3. **Hunt & scope**
   - Search for other msbuild executions with similar arguments across the fleet.
   - Pivot on dropped artifacts, child process hashes, and outbound destinations.

4. **Eradicate**
   - Remove staged project files and payloads; remediate any persistence created by follow-on activity.

## 8. SOC Relevance
High:
- Commonly seen in allowlist bypasses and “signed-binary” execution chains.
- Well-instrumented with standard Windows telemetry (4688 + Sysmon).
- Strong correlation potential when combined with module-load, file-write, and network signals.

## 12. Mitigations
- **Disable or Remove Feature or Program (M1042):** remove MSBuild where not required.
- **Execution Prevention (M1038):** block msbuild.exe on non-required systems using WDAC/AppLocker policies.

## 13. Testing & Validation
Defender-safe validation:
- Confirm msbuild.exe executions are expected on build/dev hosts and rare elsewhere.
- Run a benign, organization-approved build on a dev host and verify:
  - Process creation telemetry captures msbuild + children,
  - Module load and file creation logging functions,
  - Correlation rules do not alert in approved contexts.
- On a non-dev test endpoint, validate that policy blocks or alerts on msbuild execution.
