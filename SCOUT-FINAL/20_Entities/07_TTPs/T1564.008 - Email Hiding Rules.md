# Hide Artifacts: Email Hiding Rules (T1564.008)

## 1. Summary
Email Hiding Rules describes adversaries **creating or modifying email client or server-side rules to hide, delete, move, or suppress malicious or security-relevant messages**. This technique is used to conceal attacker communications, prevent victims from seeing security alerts, and maintain stealth during email-based compromise.

T1564.008 is commonly used to:
- Hide phishing confirmation emails
- Suppress MFA or security alert notifications
- Conceal attacker-to-attacker communications
- Maintain long-term access to compromised mailboxes

---

## 2. Technical Overview
Modern email platforms support client-side and server-side rules that automatically process messages based on defined criteria. Adversaries abuse these features by:

- Creating inbox rules that move messages to obscure folders
- Deleting messages containing security-related keywords
- Marking emails as read to avoid user attention
- Forwarding or redirecting messages while hiding originals
- Applying rules at the server level to evade client detection

Common platforms abused include:
- Microsoft Exchange / Exchange Online
- Microsoft Outlook (desktop and web)
- Google Workspace (Gmail)

Typical artifacts and indicators:
- Inbox rules created without user awareness
- Rules filtering security, MFA, or phishing-related keywords
- Missing security notifications or confirmation emails
- Audit logs showing rule creation or modification

---

## 3. Subtechnique Considerations
Key considerations for T1564.008:
- Often follows **email account compromise**
- Strongly associated with **Valid Accounts (T1078)**
- Frequently paired with **Account Manipulation (T1098)**
- Highly effective in cloud/SaaS environments

Detection requires **mailbox rule auditing**, not just message inspection.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Creating rules that auto-delete security alerts
- Moving attacker correspondence to hidden folders
- Marking inbound phishing replies as read
- Redirecting sensitive messages while hiding originals

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should focus on **rule creation and behavior**:
- Monitor for creation or modification of inbox rules
- Alert on rules targeting security or authentication keywords
- Detect rules created outside normal user behavior patterns
- Correlate rule creation with suspicious authentication events

### Data Source Notes
- **Mailbox audit logs**: Primary detection source
- **Email admin logs**: Required for server-side rule visibility
- **Identity logs**: Correlate rule changes with login anomalies

Common false positives:
- Power users with complex inbox automation
- Legitimate email organization workflows

Tuning guidance:
- Baseline normal rule usage by role
- Elevate severity for rules affecting security messages

---

## 6. Response Guidance
When suspected:
1. Enumerate all mailbox rules for affected accounts
2. Disable and remove unauthorized rules
3. Review mailbox activity for suppressed messages
4. Reset credentials and revoke active sessions
5. Investigate lateral movement via email access

## 8. SOC Relevance
T1564.008 is especially relevant in:
- Business email compromise (BEC) investigations
- Cloud identity incidents
- Situations involving missing security notifications

Email hiding rules often explain why victims report “never seeing” alerts.

---

## 9. Threat Actor Usage
This technique is commonly used by:
- BEC-focused criminal groups
- Financially motivated attackers
- Intrusion sets targeting executives and finance teams

---

## 10. Campaign Usage
Observed in:
- BEC campaigns
- Phishing-driven credential theft operations
- Long-term mailbox compromise incidents

---

## 11. Malware Usage
Typically associated with:
- Manual operator activity
- Cloud-focused intrusion toolkits
- Phishing frameworks that maintain mailbox access

---

## 12. Mitigations
Recommended mitigations:
- Enable mailbox auditing for rule creation
- Restrict who can create server-side rules
- Alert on rules affecting security-related messages
- Educate users on mailbox compromise indicators
- Implement conditional access and MFA

---

## 13. Testing & Validation
Validation approaches:
- Create benign inbox rules and verify alerts
- Test detection of rules targeting MFA/security emails
- Validate SOC playbooks for mailbox compromise
- Ensure audit logs are retained and searchable
