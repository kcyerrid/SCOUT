# Masquerading: Invalid Code Signature (T1036.001)

## 1. Summary
Invalid Code Signature describes adversaries **presenting malicious binaries as legitimately signed software while using invalid, tampered, expired, or improperly applied digital signatures**. This technique exploits trust assumptions around signed executables to evade detection and analyst scrutiny.

Attackers use this technique to:
- Appear legitimate during triage
- Bypass weak signature-presence checks
- Exploit analyst assumptions about signed binaries
- Increase dwell time through reduced suspicion

---

## 2. Technical Overview
Modern operating systems support digital signatures to verify software authenticity. Adversaries abuse this trust model by:

- Using stolen, revoked, or expired certificates
- Modifying signed binaries post-signing
- Applying malformed or incomplete signatures
- Exploiting systems that check only for signature presence, not validity

Key technical characteristics:
- Binary appears “signed” but fails full validation
- Signature chain may be incomplete or broken
- Timestamp mismatches may occur
- Signature metadata may not align with vendor expectations

Indicators include:
- Executables with invalid or unverifiable signatures
- Signed binaries executing from unusual locations
- Signature metadata inconsistent with known software
- Signature validation failures at load time

---

## 3. Subtechnique Considerations
Key considerations for T1036.001:
- Often overlaps with **Subvert Trust Controls (T1553)**
- Particularly effective against immature allowlisting
- Common in malware loaders and droppers
- Frequently paired with **Obfuscation (T1027)**

Invalid signatures exploit **partial trust validation**, not the absence of signing.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Executing binaries with expired certificates
- Using revoked signing certificates
- Modifying a signed binary after signing
- Packaging malware within improperly signed installers

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should emphasize **signature validation integrity**:
- Enforce full certificate chain validation
- Alert on invalid or revoked signatures at execution
- Detect signed binaries executing from non-standard paths
- Correlate signature anomalies with suspicious behavior

### Data Source Notes
- **Image load telemetry**: Identify signature validation failures
- **Code signing logs**: Verify certificate trust chains
- **EDR telemetry**: Correlate execution with signature state

Common false positives:
- Legacy software with expired certificates
- Internally signed enterprise tooling

Tuning guidance:
- Maintain allowlists for known internal certificates
- Elevate alerts when invalid signatures coincide with suspicious behavior

---

## 6. Response Guidance
When suspected:
1. Validate the full certificate chain and revocation status
2. Compare binary hashes against known-good software
3. Analyze execution behavior and lineage
4. Isolate systems if malicious activity is confirmed
5. Hunt for similar binaries across the environment

## 8. SOC Relevance
T1036.001 explains scenarios where:
- “Signed” malware bypasses superficial controls
- Analysts initially trust malicious binaries
- Execution is allowed despite weak validation

SOC teams must ensure **signature validity**, not just presence.

## 11. Malware Usage
Associated with:

- Backdoors using stolen certificates
- Malware attempting to bypass allowlisting

---

## 12. Mitigations
Recommended mitigations:
- Enforce strict signature validation
- Monitor certificate revocation status
- Implement application allowlisting
- Restrict execution from user-writable directories

---

## 13. Testing & Validation
Validation approaches:
- Execute benign binaries with invalid signatures in lab
- Validate alerts on signature verification failure
- Test SOC workflows for signed-but-malicious scenarios
