## 1. Summary
Port Knocking (T1205.001) hides a listener or capability behind a **predefined sequence of connection attempts to closed ports**. Only after the correct sequence is observed does the host open/enable access (often by firewall rule change or service activation), enabling stealthy persistence or command and control.

## 2. Technical Overview
- **Trigger:** A remote source rapidly touches a sequence of ports that are expected to be closed (often resulting in RST/ICMP unreachable on the wire).
- **Response:** The target host:
  - Enables/creates a firewall/ACL rule, and/or
  - Starts a service or binds a new socket, and then
  - Accepts a first successful connection (or initiates an outbound connection as part of the design).
- **Observation methods used by adversaries:** packet sniffing via capture libraries or raw socket techniques to detect the knock without requiring an active service port until triggered.

## 3. Subtechnique Considerations
- This is a sub-technique of **Traffic Signaling (T1205)**.
- Compared to **Socket Filters (T1205.002)**:
  - Port knocking is usually easier to see in **flow telemetry** (sequences of closed-port attempts).
  - Socket filters may involve fewer packets but more explicit packet-capture/raw-socket artifacts on-host.

## 4. Procedure Examples
ATT&CK documents, among others:
- [[30_CIPHER/05_Malware/S1204 - cd00r|cd00r]] monitoring for a configurable port sequence before opening a port for communication.
- [[30_CIPHER/05_Malware/S1060 - Mafalda|Mafalda]] and [[30_CIPHER/05_Malware/S1059 - metaMain|metaMain]] using a port-knocking/handshake procedure to authenticate to another implant.
- [[30_CIPHER/03_Threat_Actors/G0056 - PROMETHIUM|PROMETHIUM]] configuring `knockd` and firewall rules to only accept C2 after a specified knock sequence.
- [[30_CIPHER/03_Threat_Actors/G1048 - UNC3886|UNC3886]] maintaining persistence on FortiGate firewalls via ICMP port knocking.

## 5. Detection Guidance
**Primary detection goal:** sequence-of-failures → host state change → first success.

**Network detections:**
- **Knock sequence detection (flow-based):**
  - Same source → same destination host: multiple distinct destination ports within a short window.
  - Predominantly failed attempts (S0 / RST / ICMP unreachable), then a successful connection shortly after.
- **ICMP-based knocking (device-focused):**
  - Repeating ICMP patterns from a single source preceding management session success.

**Host detections (correlation-critical):**
- **Firewall/ACL modifications** within the correlation window:
  - Windows Firewall eventing (WFP rule changes)
  - Linux/macOS firewall tools (`iptables`, `nft`, `ufw`, `pfctl`, socketfilterfw)
- **New listener bind/service enablement** shortly after the knock sequence:
  - “Previously closed port now listening” events (endpoint or device telemetry)

**Tuning guidance:**
- Set a correlation time window (e.g., 60–300 seconds) and minimum sequence length (≥3 ports).
- Allowlist expected firewall changers (patch/management agents) and known scanner sources to reduce noise.

### 5.1. Data Source Notes
- **Network Traffic Flow / Network Connection Creation:** Needed to detect knock sequences and “first successful connect” transitions.
- **Process Creation:** Needed to see firewall tool execution and service starts that implement the knock response.

## 6. Response Guidance
1. **Contain**
   - Temporarily block the source(s) generating knock patterns and restrict access to newly opened ports.
2. **Investigate**
   - Identify what changed on the host/device (rules, services, configs).
   - Determine the process/account responsible for rule or service changes.
3. **Eradicate**
   - Remove unauthorized knock daemons/scripts and revert firewall/ACL changes.
   - Validate device integrity (especially on edge appliances).
4. **Recover & Harden**
   - Implement strict inbound management segmentation and MFA on management planes.
   - Reduce the set of principals authorized to modify firewall/ACL state.

## 12. Mitigations
- **Filter Network Traffic:** Use stateful firewalls/ACLs and segmentation; tightly restrict inbound access to management/listener ports and monitor for rule changes.

## 13. Testing & Validation
- Validate with authorized lab tests:
  - Generate controlled knock sequences and verify flow telemetry captures them.
  - Trigger expected firewall/service changes and confirm correlation-based alerting.
  - Confirm allowlists (expected scanners, admin tools) suppress benign sequences.
