# Masquerading: Break Process Trees (T1036.009)

## 1. Summary
Break Process Trees describes adversaries **intentionally disrupting or obscuring parent–child process relationships** so that malicious activity appears detached from its true origin. By breaking or manipulating process lineage, attackers reduce the effectiveness of detections that rely on execution chains.

Attackers use this technique to:
- Evade lineage-based detections
- Obscure the true source of execution
- Complicate forensic reconstruction
- Blend malicious processes into background system activity

---

## 2. Technical Overview
Many security tools rely on process trees to understand execution context. Adversaries undermine this visibility by:

- Spawning processes via APIs that detach from parents
- Terminating parent processes after child execution
- Using job control, daemonization, or orphaning techniques
- Leveraging container or service boundaries to reset lineage
- Executing payloads via indirect or native APIs

Key characteristics:
- Orphaned or re-parented processes
- Unexpected root processes without clear ancestry
- Short-lived parents followed by long-running children
- Execution chains inconsistent with user or system activity

Indicators include:
- Processes with missing or anomalous parents
- Execution without corresponding user interaction
- Detached processes performing suspicious actions
- Incomplete or inconsistent process trees

---

## 3. Subtechnique Considerations
Key considerations for T1036.009:
- Strong overlap with **Native API Execution (T1106)**
- Commonly paired with **Process Injection (T1055)**
- Often combined with **Indicator Removal (T1070)**
- Particularly effective against EDRs that rely heavily on lineage

Breaking process trees targets **detection logic**, not execution capability.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Launching processes that intentionally orphan themselves
- Spawning payloads via APIs that suppress lineage
- Terminating parent processes immediately after execution
- Using service or container boundaries to reset ancestry

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should emphasize **behavioral anomalies over lineage completeness**:
- Detect orphaned or re-parented processes
- Alert on suspicious activity from root-level processes
- Correlate execution with API usage and timing
- Monitor for parent termination shortly after child creation

### Data Source Notes
- **Process creation telemetry**: Identify missing or abnormal parents
- **Process termination logs**: Correlate parent exit timing
- **EDR telemetry**: Provide enriched lineage and API context

Common false positives:
- Legitimate daemonization behavior
- System services and schedulers
- Containerized workloads

Tuning guidance:
- Baseline expected orphan processes per environment
- Elevate severity when detached processes perform high-risk actions

---

## 6. Response Guidance
When suspected:
1. Identify the detached or orphaned process
2. Reconstruct likely execution path using timestamps and API logs
3. Analyze behavior and resource usage
4. Isolate affected systems if malicious activity is confirmed
5. Hunt for similar lineage breaks across the environment

## 8. SOC Relevance
T1036.009 is especially relevant when:
- Malicious processes lack clear parents
- Execution appears “out of nowhere”
- Lineage-based detections fail

SOC teams must correlate **time, behavior, and system context**, not just trees.

## 12. Mitigations
Recommended mitigations:
- Monitor orphaned and re-parented processes
- Enrich process telemetry with API context
- Correlate execution with user and system events
- Apply behavior-based detections

---

## 13. Testing & Validation
Validation approaches:
- Simulate benign orphan process creation in lab
- Validate alerts on lineage anomalies
- Test SOC workflows for broken process trees
- Ensure detections are not solely lineage-dependent
