## 1. Summary
DCSync (T1003.006) is the abuse of Active Directory replication APIs to simulate domain controller replication and pull credential material (including password hashes) from a domain controller. It is highly impactful because it can be performed remotely once the attacker has the right AD replication permissions, often without needing to access NTDS.dit directly.

## 2. Technical Overview
How DCSync works (defender-focused):
- AD replication uses Directory Replication Service (DRS) mechanisms to synchronize directory objects between domain controllers.
- An attacker with appropriate permissions (e.g., replication-related rights) can request replication data for targeted accounts and extract hashes.
- The technique is frequently used to obtain high-value credentials such as KRBTGT and privileged accounts, enabling follow-on actions such as forged tickets and broad privilege escalation.

Key behaviors:
- **Replication requests from non-DC endpoints**
- **High-value account targeting**
- **Rapid follow-on credential usage** (Kerberos ticket anomalies, privileged logons, lateral movement)

## 3. Subtechnique Considerations
- DCSync can be “stealthier” than NTDS file copying (T1003.003) because it relies on API calls and permission abuse rather than heavy file artifacts.
- Detection is identity-centric: focus on replication rights, directory service logs, and replication request patterns.

## 5. Detection Guidance
This is a **top-tier detection priority** for Windows domains.

High-signal detection patterns:
- **Replication API invocation from unusual hosts**
  - Replication requests originating from non-domain-controller endpoints.
  - Replication operations initiated by accounts that do not normally perform directory replication.
- **Permissions-based detections**
  - Changes to AD objects/ACLs granting replication-related rights to users/groups that historically did not have them.
  - New service principals or accounts gaining replication rights shortly after privilege escalation events.
- **Targeting patterns**
  - Replication requests focusing on high-value accounts (e.g., KRBTGT, Domain Admins) or a burst of many accounts in a short window.
- **Follow-on correlation**
  - DCSync indicators followed by anomalous ticket behavior, mass logons, or sudden privilege escalation across the estate.

### Data Source Notes
Useful telemetry sources:
- Domain controller directory service and security auditing (replication-related events where available)
- AD change auditing for permissions/ACL modifications (replication rights)
- Identity analytics for unusual privileged account behavior post-event
- Endpoint/network telemetry for replication tool execution and lateral movement correlation

## 6. Response Guidance
- **Immediate containment**
  - Revoke suspicious sessions/tokens; isolate suspected operator endpoints.
  - Remove unauthorized replication permissions; review and correct AD ACLs.
- **Credential actions**
  - Treat as domain compromise risk: rotate privileged credentials; plan KRBTGT resets (proper sequencing and validation).
- **Scope**
  - Identify all replication requests and which accounts’ data was accessed.
  - Hunt for persistence: new accounts, delegated rights, golden ticket indicators, and abnormal trust changes.
- **Recovery**
  - Consider full domain incident response playbook steps; verify DC integrity and administrative tiering.

## 8. SOC Relevance
- One of the strongest indicators of **domain takeover attempt**.
- Best SOC pivots:
  - Source host and initiating account for replication calls
  - Recent AD ACL changes granting replication rights
  - Immediate post-event identity anomalies (tickets, privileged logons, lateral movement)

## 12. Mitigations
- **M1015 - Active Directory Configuration**: tightly manage and audit “Replicating Directory Changes” and related replication permissions/ACLs.
- **M1027 - Password Policies**: ensure unique, complex local admin passwords and strong privileged password hygiene.
- **M1026 - Privileged Account Management**: enforce tiered admin, limit privilege sprawl, and monitor privileged account usage closely.

## 13. Testing & Validation
- In a lab AD environment:
  - Validate detections for replication API abuse from non-DC endpoints.
  - Test alerting for unauthorized assignment of replication rights.
  - Validate SOC runbooks for KRBTGT reset planning and privilege containment.
- Ensure detections are resilient to tooling changes by focusing on replication behavior rather than single tool signatures.
