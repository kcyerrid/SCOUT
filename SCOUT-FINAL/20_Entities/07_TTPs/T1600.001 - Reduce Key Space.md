## Summary
**Weaken Encryption: Reduce Key Space (T1600.001)** covers adversary behavior that reduces cryptographic key size/strength on a compromised network device, lowering the effort required to decrypt protected information. 

## Technical Overview
Reducing key space typically manifests as:
- downgrading allowed key lengths (e.g., minimum RSA modulus / DH group strength),
- enabling weaker ciphersuites or legacy protocol versions,
- altering device policy so sessions negotiate reduced-strength cryptography.

This is especially impactful when:
- devices terminate VPNs (site-to-site, remote access),
- devices enforce TLS inspection/termination,
- management plane encryption settings are weakened.

## Subtechnique Considerations
This is a subtechnique of **T1600 Weaken Encryption**.   
Use this note when evidence points specifically to **key size/cipher downgrade** (not crypto hardware disablement).

## Procedure Examples
Defender-observable patterns (non-operational):
- Config deltas that set smaller keys, enable weak cipher lists, or reintroduce deprecated algorithms.
- Administrative activity modifying crypto sections followed by traffic negotiation shifts.

## Detection Guidance
MITRE’s detection strategy for T1600.001 emphasizes identifying crypto configuration changes that downgrade key strength/ciphers and correlating with observed weaker negotiation in traffic. 

High-signal detection angles:
1. **Config change detection (crypto policy deltas)**
   - Alert on reductions to minimum key sizes, adding weak algorithms, or enabling deprecated protocol versions.
2. **CLI command monitoring**
   - Flag crypto-policy related commands outside approved windows or by nonstandard admin accounts.
3. **Traffic negotiation monitoring**
   - Detect when sessions negotiate weaker suites/versions than baseline for the same peers/services.

### Data Source Notes
Relevant ATT&CK telemetry categories include **File**, **Command**, and **Network Traffic**.   
From MITRE’s detection strategy log sources, defenders should ensure coverage for:
- configuration/file modification events,
- command execution logs (network device CLI),
- network traffic content/flow indicators showing downgrade. 

## Response Guidance
1. **Confirm scope**
   - Identify affected interfaces, tunnels, and services; compare negotiated parameters to baseline.
2. **Rollback**
   - Revert crypto settings to last-known-good; reapply approved cipher/key baselines.
3. **Credential & access review**
   - Investigate admin account misuse; rotate secrets if compromise suspected.
4. **Assurance**
   - Validate restored posture via traffic negotiation checks and device compliance scans.

## SOC Relevance
This subtechnique is a strong indicator of **intentional confidentiality degradation**. It’s often missed if you only monitor “any config change” without semantic parsing of crypto settings. Build SOC detections that specifically classify crypto deltas as **strengthening vs. weakening**.

## Mitigations
- Enforce minimum cryptographic standards (policy-as-code; compliance gates).
- Restrict crypto configuration privileges; require MFA + approvals.
- Implement continuous drift detection focused on crypto parameters.
- Monitor negotiated crypto characteristics at the edge and alert on downgrade.

## Testing & Validation
- Unit-test config parsers against known-good and known-weak profiles.
- Run a controlled, authorized change (lab/nonprod) that reduces key size and verify:
  - config drift alert triggers,
  - traffic negotiation alert triggers,
  - rollback playbook restores posture.
