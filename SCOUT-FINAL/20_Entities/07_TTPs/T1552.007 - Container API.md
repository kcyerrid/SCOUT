## 1. Summary
Adversaries may abuse container environment APIs (e.g., Docker API, Kubernetes API) to obtain credentials or secrets. Misconfigured or overly permissive access to these APIs can allow an attacker to enumerate secrets, read logs containing credentials, or harvest service account tokens—often enabling rapid cluster takeover or cloud pivoting.

## 2. Technical Overview
Container orchestration and runtime APIs provide management capabilities, including:
- Retrieving workload logs (which may leak credentials, tokens, or endpoints)
- Enumerating and retrieving stored secrets
- Accessing service account identities and related credentials

Common preconditions:
- Network reachability to API endpoints (or access to the Docker socket)
- Stolen credentials/service account tokens, weak RBAC, or exposed unauthenticated APIs

Common adversary outcomes:
- Credential/secrets theft → lateral movement within cluster → access to cloud resources, registries, CI/CD, or data stores.

## 3. Subtechnique Considerations
- **Kubernetes vs. Docker**: telemetry and security controls differ; detections must be platform-aware.
- **Legitimate automation**: CI/CD and cluster operators may query APIs regularly—baseline expected callers and namespaces.
- **Service accounts**: least privilege mistakes can lead to high-impact secret exposure.

## 4. Procedure Examples
Observed usage includes:
- Malware querying Kubernetes APIs to retrieve secrets from clusters.

## 5. Detection Guidance
**Kubernetes API monitoring**
- Detect unusual `get/list` activity against secrets and config resources:
  - Non-admin identities performing bulk access
  - New user agents or unusual source pods/nodes
  - Access across many namespaces in a short time window

**Docker API monitoring**
- Detect remote access to Docker daemon endpoints or socket usage by non-baselined processes.
- Correlate log retrieval patterns with subsequent outbound connections or archive creation.

**Behavioral correlation**
- Alert sequences:
  1) API access to secrets/logs
  2) token usage to call additional cluster endpoints
  3) follow-on actions such as new pods, privilege changes, or external data egress

### Data Source Notes
- Kubernetes audit logs, API server logs, admission controller/WAF logs (if used), node eBPF/network telemetry, and container runtime logs.
- Enrich alerts with: namespace, service account, node, pod labels, and RBAC bindings.

## 6. Response Guidance
1. **Containment**
   - Revoke/rotate exposed service account tokens and secrets; isolate affected namespaces.
2. **Access restriction**
   - Enforce RBAC least privilege; remove wildcard permissions; prefer scoped RoleBindings.
3. **Credential hygiene**
   - Rotate any leaked credentials found in logs or secrets; validate no reuse in CI/CD.
4. **Hunt**
   - Investigate for cluster persistence: new service accounts, role bindings, daemonsets, or privileged pods.
5. **Hardening**
   - Restrict API server exposure; secure Docker daemon access; implement network policies.

## 12. Mitigations
- **M1035 - Limit Access to Resource Over Network**: Restrict API access to secured channels; require TLS and authenticated access.
- **M1030 - Network Segmentation**: Reduce direct remote access paths to internal container management services.
- **M1026 - Privileged Account Management**: Apply least privilege for service accounts; disable default service accounts where possible.
- **M1018 - User Account Management**: Enforce strong authentication and RBAC; prefer namespace-scoped bindings.
