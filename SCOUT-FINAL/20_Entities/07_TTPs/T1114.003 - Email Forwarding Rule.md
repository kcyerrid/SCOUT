## 1. Summary
Adversaries create or modify email forwarding rules to automatically copy messages to other recipients/locations. This enables silent collection, supports intelligence gathering, and can maintain access to emails even after password resets if the rule persists.

## 2. Technical Overview
Forwarding rule abuse may involve:
- **Inbox rules** (client/server-side) that forward or redirect messages.
- **Transport/mail flow rules** that apply tenant-wide or org-wide logic (e.g., forwarding all inbound/outbound mail to an attacker-controlled address).
- **Hidden rules** (e.g., modified via MAPI) not visible in standard UI/admin tools.

Defender-relevant signals:
- Creation/modification of forwarding/redirect rules, especially to **external recipients**.
- Rule creation shortly after risky sign-in, MFA bypass, or privilege escalation.
- Mail headers or metadata indicative of auto-forwarding (environment-dependent).
- New or unusual admin cmdlets used to create transport rules.

## 3. Subtechnique Considerations
- Platform differences:
  - **Office Suite/Exchange**: inbox rules, mailbox forwarding settings, and transport rules are primary.
  - **macOS/Linux**: mail clients and filtering/forwarding mechanisms differ; detections may rely on client configuration changes.
- Hidden rules are a common evasive angle—ensure you can detect **rule state changes** even if UI visibility is suppressed.

## 4. Procedure Examples
Examples observed in ATT&CK procedure examples include:
- [[30_CIPHER/03_Threat_Actors/G0094 - Kimsuky|Kimsuky]] setting auto-forward rules on victim accounts.
- [[30_CIPHER/03_Threat_Actors/G1004 - LAPSUS$|LAPSUS$]] setting tenant-level mail transport rules to forward organizational mail.
- [[30_CIPHER/03_Threat_Actors/G1015 - Scattered Spider|Scattered Spider]] redirecting notification emails.
- [[30_CIPHER/03_Threat_Actors/G1033 - Star Blizzard|Star Blizzard]] abusing forwarding rules to monitor victims and maintain access.

## 5. Detection Guidance
High-signal detections
- **New/modified forwarding rules**:
  - any forwarding to external domains,
  - forwarding enabled on high-value mailboxes,
  - forwarding rules created by admins on user mailboxes without change ticket.
- **Transport/mail flow rule creation**:
  - rules affecting broad scopes (all users/all mail),
  - rules routing to newly created accounts or unusual recipients.
- **Hidden rule indicators**:
  - mismatch between rule audit logs and UI-reported state,
  - rule property changes consistent with “hidden” flags (implementation-specific).
- **Correlation**:
  - rule creation + abnormal sign-in + mailbox access or export activity.

Recommended SOC triage fields
- actor account, affected mailbox, rule name/conditions/actions, forward-to address, creation/modification time, source IP/device, admin vs user context.

### Data Source Notes
- Ensure logging captures:
  - rule creation/modification/removal events,
  - cmdlet execution (e.g., inbox/transport rule management),
  - identity sign-in context (MFA, conditional access, geo/device).
- Retain sufficient history to detect “slow burn” persistence via forwarding rules.

## 6. Response Guidance
1) **Contain**
- Disable/remove suspicious forwarding and transport rules immediately.
- Revoke sessions and rotate credentials for the impacted account(s).
- If org-wide transport rules were abused, treat as a high-severity incident.

2) **Scope**
- Determine how long rules existed and what mail was forwarded (recipients, time range).
- Identify initial access vector (phishing, credential theft, MFA fatigue, token theft).

3) **Remediate**
- Enforce policy restricting external auto-forwarding.
- Implement change control around transport rules and mailbox forwarding settings.

## 12. Mitigations
- **M1047 Audit**: Regularly audit inbox rules/transport rules and investigate deviations.
- **M1042 Disable or Remove Feature or Program**: Consider disabling external auto-forwarding where feasible.
- **M1041 Encrypt Sensitive Information**: Use encryption for sensitive email content where feasible.
- **M1060 Out-of-Band Communications Channel**: Use OOB verification for sensitive actions and OOB alerts for unusual forwarding behavior.

## 13. Testing & Validation
- In a controlled environment:
  - Create a benign forward-to-internal rule, then a forward-to-external rule (if policy permits) and confirm alerts.
  - Create a mail flow/transport rule with broad scope and confirm high-severity detection.
- Validate detections cover:
  - user-created inbox rules,
  - admin-created inbox rules,
  - transport/mail flow rules,
  - and include source IP/device context.
