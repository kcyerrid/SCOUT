# T1021.004 - SSH

## 1. Summary
Adversaries use Secure Shell (SSH) to authenticate to and interact with remote systems for lateral movement. SSH is common across Linux/macOS environments and may also be present on Windows and ESXi.

## 2. Technical Overview
Typical attacker patterns:
- SSH logins using valid credentials (stolen passwords, keys, or federated identities).
- Interactive shell activity after login (commands, file transfer, persistence setup).
- Use of bastions/jump hosts (legitimate or compromised) to pivot and blend with normal administrative workflows.

High-signal indicators:
- SSH from new source hosts/subnets or unusual geographies (where externally exposed).
- SSH by accounts that do not normally use interactive shells.
- SSH session followed by privilege escalation actions (e.g., sudo/su) and additional outbound connections.

## 3. Subtechnique Considerations
This is a subtechnique of [[20_Entities/07_TTPs/TA0008 - Lateral Movement/T1021 - Remote Services|T1021]].
- SSH logs and telemetry quality varies widely by OS and configuration; ensure SSHD logging and centralized collection are consistently implemented.
- On ESXi, SSH access is often tightly controlled; any unexpected enablement or login can be high severity.

## 5. Detection Guidance
Focus on: **new/rare SSH access + suspicious post-auth activity**.

Detection ideas:
- Alert on SSH authentication success:
  - From a new source IP/host for that user or target.
  - To sensitive assets (infrastructure servers, hypervisors, management nodes).
  - Outside expected maintenance windows.
- Correlate SSH sessions with:
  - Privilege escalation commands (sudo/su) and new account/key additions.
  - Suspicious process execution, persistence changes (cron/systemd), or log tampering.
  - Outbound lateral movement from the newly accessed host.

### 5.1. Data Source Notes
Useful telemetry typically includes:
- SSHD authentication logs (accepted/failed, method, source IP, username).
- Command audit telemetry (where deployed) for high-risk commands post-login.
- Network telemetry for TCP/22 (and alternative SSH ports), plus session metadata.
- Endpoint telemetry for persistence changes (authorized_keys edits, service config changes).

## 6. Response Guidance
- Contain: isolate affected host if malicious activity is confirmed; restrict SSH to approved admin networks/bastions.
- Credentials: rotate keys/passwords; invalidate stolen keys; enforce MFA where possible for admin workflows.
- Scope: identify other hosts accessed by the same user/source; search for new keys, new users, and persistence mechanisms.
- Hardening: disable password auth where feasible, enforce key policies, restrict by network and allowlists, and monitor SSH enablement changes.

## 8. SOC Relevance
Key pivots:
- Source IP/host reputation and whether it is a known bastion.
- Authentication method (key vs password), and whether it changed from baseline.
- Post-auth command execution and configuration changes (keys, sudoers, sshd_config).
- Evidence of additional pivoting from the host after SSH access.

## 12. Mitigations
ATT&CK-listed mitigations for T1021.004 include:
- M1042 Disable or Remove Feature or Program: disable SSH if it is not necessary.
- M1035 Limit Access to Resource Over Network: allow SSH only from specific IPs; enforce firewall rules; restrict by user.
- M1027 Password Policies: require long, complex passwords; consider disabling password auth where feasible.
- M1026 Privileged Account Management: limit privileged account use; enforce least privilege for remote administration.
- M1018 User Account Management: limit which accounts can use SSH and what they can run; restrict shell access where feasible.

## 13. Testing & Validation
- Confirm SSHD logs (success/failure, source, auth method) are centrally collected and time-synced.
- Simulate authorized SSH from bastion vs. unauthorized subnet in a lab and verify alerting works.
- Validate detection of key additions and sshd_config changes via file integrity monitoring.
