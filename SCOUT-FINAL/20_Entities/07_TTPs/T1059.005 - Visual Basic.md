# Visual Basic (T1059.005)

## 1. Summary
Visual Basic describes adversary abuse of Visual Basic–based scripting technologies, primarily VBScript and legacy Visual Basic execution mechanisms, to run malicious code on Windows systems. This subtechnique is commonly used for initial execution, payload staging, and automation in phishing and malware delivery campaigns.

Because VBScript is a legacy technology still supported in many environments, its malicious use may evade modern security controls if not explicitly monitored.

---

## 2. Technical Overview
Visual Basic–based scripts can be executed through:
- `wscript.exe` and `cscript.exe`
- Embedded scripts in HTML Applications (`.hta`)
- Office documents with Visual Basic for Applications (VBA)
- Dropped `.vbs` script files

Adversaries use Visual Basic scripting to execute commands, download payloads, and interact with the Windows API. Artifacts include script file creation, interpreter process execution, and child processes spawned by the script host.

---

## 3. Subtechnique Considerations
T1059.005 focuses on standalone Visual Basic scripting execution and does **not** include Office VBA, which is tracked separately.

Key considerations include:
- Legacy environments where VBScript remains enabled
- Script execution via trusted host processes
- Limited native logging compared to modern scripting engines

Detection often requires enhanced process and file visibility.

---

## 4. Procedure Examples
Observed adversary procedures include:
- Executing `.vbs` scripts delivered via phishing
- Using VBScript to download and execute second-stage payloads
- Embedding scripts in `.hta` files for execution
- Leveraging Windows Script Host to automate execution

Analysts may observe `wscript.exe` or `cscript.exe` spawning network-aware child processes.

---

## 5. Detection Guidance
Detection should focus on:
- Execution of VBScript interpreters in non-administrative contexts
- Script execution originating from user-writable directories
- Scripts spawning PowerShell, cmd.exe, or other interpreters
- Network connections initiated by script host processes

Correlation between process execution and file creation improves fidelity.

### Data Source Notes
- **Process Execution:** Primary detection source
- **File Creation:** Useful for identifying dropped scripts
- **Script Logs:** Limited; often require endpoint tooling

---

## 6. Response Guidance
When malicious Visual Basic scripting is suspected:
- Capture and preserve script files
- Identify follow-on payloads or execution stages
- Isolate affected endpoints if execution is confirmed
- Review email or delivery vectors associated with the script

Preserve script host execution artifacts for forensic analysis.

## 8. SOC Relevance
Visual Basic scripting remains relevant due to legacy support and continued use in phishing and malware campaigns. SOCs should ensure visibility into script host execution, especially in user environments.

## 9. Threat Actor Usage
This subtechnique is used by:
- Commodity malware operators
- Phishing-based threat actors
- Initial access brokers

Confidence in moderate but persistent usage is medium.

## 10. Campaign Usage
Visual Basic execution has appeared in:
- Email-based malware delivery campaigns
- Initial access phases of ransomware intrusions
- Legacy enterprise environment compromises

## 12. Mitigations
Effective mitigations include:
- Disabling Windows Script Host where possible
- Restricting execution of `.vbs` and `.hta` files
- Enforcing least-privilege principles
- Monitoring script interpreter execution
- Applying email and attachment filtering

---

## 13. Testing & Validation
Validation approaches include:
- Atomic Red Team tests for VBScript execution
- Purple team simulations using script-based payloads
- Review of alerts tied to script host activity

Successful validation results in detection of unauthorized Visual Basic script execution.
