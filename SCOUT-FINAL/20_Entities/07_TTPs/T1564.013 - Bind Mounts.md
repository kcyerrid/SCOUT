# Hide Artifacts: Bind Mounts (T1564.013)

## 1. Summary
Bind Mounts describes adversaries **using filesystem bind mounts to obscure or redirect access to files and directories**, effectively hiding malicious artifacts or altering the apparent filesystem layout. This technique is most commonly observed on Linux systems and within containerized environments.

By leveraging bind mounts, attackers can:
- Conceal malicious files behind benign paths
- Redirect file access without modifying binaries
- Evade file-based detection and monitoring
- Maintain stealth in container and cloud workloads

---

## 2. Technical Overview
Bind mounts allow an existing directory or file to be mounted at an alternate location in the filesystem tree. Unlike traditional mounts, bind mounts do not require a separate filesystem — they simply expose the same underlying data through a different path.

Adversaries abuse this capability by:
- Mounting malicious directories over legitimate system paths
- Redirecting access away from monitored locations
- Hiding payloads beneath benign directory structures
- Obscuring forensic visibility during live response

Common environments:
- Linux servers
- Container runtimes (Docker, containerd, Kubernetes)
- Cloud-hosted Linux workloads

Typical artifacts include:
- Unexpected or transient mount entries
- Files accessible via multiple paths
- Discrepancies between on-disk structure and runtime view
- Container file paths inconsistent with images

---

## 3. Subtechnique Considerations
Key considerations for T1564.013:
- Primarily relevant to Linux and containerized environments
- Often combined with **Indicator Removal on Host (T1070)**
- Highly effective against file-path-based detections
- Detection requires visibility into mount operations

Bind mounts are often ephemeral, making post-incident reconstruction difficult.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Using bind mounts to overlay benign directories on top of malicious content
- Hiding backdoor binaries beneath legitimate filesystem paths
- Redirecting logging directories to suppress evidence
- Manipulating container filesystem views at runtime

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should focus on **mount activity and filesystem discrepancies**:
- Monitor for unexpected bind mount creation
- Alert on mount changes outside provisioning workflows
- Correlate mount operations with suspicious process execution
- Detect filesystem overlays inconsistent with baseline images

### Data Source Notes
- **Mount and syscall telemetry**: Critical for detection
- **Container runtime logs**: Required in Kubernetes and Docker
- **Process telemetry**: Identify who initiated mount actions

Common false positives:
- Legitimate container runtime operations
- System administration activities
- Configuration management tooling

Tuning guidance:
- Baseline expected mount behavior per workload
- Elevate alerts when mounts coincide with execution anomalies

---

## 6. Response Guidance
When suspected:
1. Enumerate active mounts and bind mounts
2. Identify hidden or redirected filesystem paths
3. Preserve runtime state before reboot
4. Investigate container images and entrypoints
5. Rebuild affected systems or containers from trusted images

---

## 12. Mitigations
Recommended mitigations:
- Restrict mount and bind-mount privileges
- Monitor and audit mount operations
- Enforce least privilege in containers
- Use immutable infrastructure where possible
- Rebuild compromised containers rather than cleaning in place

---

## 13. Testing & Validation
Validation approaches:
- Create benign bind mounts in lab environments
- Validate alerts on unauthorized mount activity
- Test SOC workflows for container filesystem analysis
- Ensure runtime telemetry is retained
