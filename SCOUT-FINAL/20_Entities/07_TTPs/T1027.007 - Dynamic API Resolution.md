# Obfuscated Files or Information: Dynamic API Resolution (T1027.007)

## 1. Summary
Dynamic API Resolution describes adversaries **resolving system API functions at runtime instead of statically linking or referencing them**, obscuring the true capabilities and intent of malicious code. This technique evades static analysis and signature-based detections that rely on import tables or known API references.

Adversaries use this technique to:
- Hide functionality during static inspection
- Reduce observable imports and strings
- Evade detection based on known API usage
- Enable flexible or environment-specific behavior

---

## 2. Technical Overview
Rather than statically importing APIs, adversaries dynamically locate and resolve functions during execution. Common approaches include:

- Enumerating loaded modules in memory
- Resolving function addresses by hashing names
- Using runtime library loading mechanisms
- Employing custom loaders to locate APIs
- Obfuscating API names until runtime

Typical behaviors:
- Minimal or empty import tables
- Runtime traversal of module export tables
- String decryption just prior to API invocation
- Indirect or function-pointer–based API calls

Indicators include:
- Hash-based API resolution routines
- Memory access patterns consistent with export table parsing
- Absence of expected imports despite complex behavior
- API calls originating from dynamically resolved addresses

---

## 3. Subtechnique Considerations
Key considerations for T1027.007:
- Extremely common in advanced malware
- Often paired with **Native API (T1106)** usage
- Enables cross-version compatibility
- Reduces reliability of static detection alone

Dynamic API resolution focuses on **runtime concealment rather than payload hiding**.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Resolving critical APIs via hashed lookups
- Loading libraries dynamically and resolving functions
- Decrypting API names only at execution time
- Executing core logic through indirect API calls

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should emphasize **runtime behavior and call patterns**:
- Monitor API calls that lack static imports
- Detect suspicious export table enumeration
- Identify decryption or hashing routines preceding API usage
- Correlate dynamic resolution with malicious actions

### Data Source Notes
- **API call tracing**: Identify unusual resolution patterns
- **Memory analysis**: Detect runtime import reconstruction
- **EDR telemetry**: Correlate indirect API usage

Common false positives:
- Legitimate software using plugin architectures
- Commercial protectors or DRM systems

Tuning guidance:
- Baseline legitimate dynamic resolution usage
- Elevate alerts when dynamic resolution enables malicious behavior

---

## 6. Response Guidance
When suspected:
1. Capture memory to observe resolved APIs
2. Analyze resolution routines and hashes
3. Identify behaviors enabled by resolved functions
4. Hunt for similar resolution patterns
5. Update detections to focus on behavior, not imports

- API-based detections may be bypassed
- Runtime visibility becomes mandatory

SOC teams should rely on **behavioral telemetry and memory inspection**.

## 12. Mitigations

- Monitor for suspicious memory access patterns
- Limit execution of untrusted binaries
- Use sandboxing to observe dynamic resolution
