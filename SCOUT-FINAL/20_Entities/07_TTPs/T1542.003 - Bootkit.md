# Pre-OS Boot: Bootkit (T1542.003)

## 1. Summary
Bootkit describes adversaries **modifying bootloader components or early boot execution paths** to run malicious code before the operating system fully initializes. Because bootkits operate before many endpoint security controls are active, they provide high-confidence persistence and can enable stealthy privilege escalation and defense evasion.

Adversaries use this technique to:
- Establish durable persistence that survives reboots
- Execute malicious code before OS security tooling initializes
- Tamper with OS startup to load implants or disable protections
- Maintain privileged control even after partial remediation

---

## 2. Technical Overview
Bootkits typically target artifacts involved in the boot chain, such as:
- Windows Boot Manager / BCD configuration and related boot components
- Linux bootloaders (e.g., GRUB) and initramfs
- macOS boot components and early startup configuration

Common bootkit behaviors include:
- Modifying bootloader binaries or configuration to load attacker code
- Introducing a malicious pre-OS stage that patches the kernel or system components at boot
- Redirecting execution flow to attacker-controlled code, then resuming normal boot to avoid user suspicion
- Persisting in partitions or disk regions less commonly monitored by standard tools

Indicators include:
- Unexpected changes to bootloader files/configuration
- Boot-time integrity check failures
- Kernel or security component anomalies immediately after boot
- Persistence that remains after OS-level cleanup actions

---

## 3. Subtechnique Considerations
Key considerations for T1542.003:
- Often requires elevated privileges, physical access, or exploitation to modify boot artifacts
- Detection is difficult without boot integrity monitoring and disk forensics
- Remediation often requires rebuilding the boot chain from trusted media (and sometimes firmware verification)
- May be combined with defense impairment to suppress warnings or telemetry post-boot

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Modifying boot configuration to load an attacker-controlled component before OS startup
- Installing a malicious bootloader stage that patches kernel security features during initialization
- Persisting code in less-monitored disk areas and invoking it from the boot chain

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should prioritize **integrity monitoring and boot-chain validation**:
- Monitor hashes and known-good baselines for bootloader binaries/configuration
- Alert on unexpected writes to boot partitions or bootloader directories
- Correlate boot-time anomalies with subsequent system behavior (e.g., disabled security tooling)
- Use disk forensics to identify hidden or altered boot components

### Data Source Notes
- **Boot logs**: Identify abnormal boot sequences and integrity warnings
- **Disk forensics**: Validate boot sectors/partitions and discover tampering
- **Firmware/boot integrity monitoring**: Detect drift from trusted states
- **EDR telemetry**: Useful post-boot for detecting disabled defenses or unusual kernel-level behaviors

Common false positives:
- Legitimate OS updates that modify boot components
- Disk encryption or bootloader changes due to authorized IT maintenance

Tuning guidance:
- Baseline expected boot changes during patch cycles
- Require change control correlation for bootloader modifications
- Elevate severity when boot changes are followed by defense impairment

---

## 6. Response Guidance
When suspected:
1. Isolate the host and preserve volatile evidence where possible
2. Acquire disk images (including boot partitions) for forensic analysis
3. Validate Secure Boot / boot integrity state and compare against baselines
4. Rebuild the boot chain from trusted media; validate firmware where appropriate
5. Hunt environment-wide for similar boot artifact modifications and related anomalies

## 8. SOC Relevance
T1542.003 is critical because:
- It can neutralize or bypass OS-level security controls early in the boot sequence
- It may survive common remediation workflows if boot artifacts are not rebuilt
- Investigation requires cross-discipline response (endpoint, forensics, platform engineering)

SOC teams should treat suspected bootkit activity as **highest severity**, with an assumption of deep compromise until proven otherwise.

---

## 9. Threat Actor Usage
Commonly used by:
- Highly capable intrusion groups
- Nation-state operators
- Advanced persistence-focused adversaries

---

## 10. Campaign Usage
Observed in:
- Long-dwell espionage intrusions
- Stealth persistence campaigns targeting high-value systems
- Attacks requiring resilience against OS rebuilds and standard IR

---

## 11. Malware Usage
Associated with:
- Bootkits
- Pre-OS loaders
- Kernel-patching persistence components

---

## 12. Mitigations
Recommended mitigations:
- Enforce Secure Boot where applicable and monitor its state continuously
- Implement boot-chain integrity monitoring and alerting
- Restrict access to boot partitions and boot configuration modifications
- Maintain rapid rebuild procedures for boot components from trusted sources
- Apply least privilege and strong change controls for system-level maintenance

---

## 13. Testing & Validation
Validation approaches:
- Verify Secure Boot enforcement and alerting on state changes
- Conduct tabletop exercises for boot compromise scenarios
- Validate ability to acquire and analyze boot partitions in forensics workflows
- Test monitoring for unauthorized writes to bootloader paths and configuration

Include:
- Preconditions: boot integrity monitoring enabled; baselines captured
- Required roles/tools: endpoint engineering, DFIR, platform admin; disk imaging tooling
- Expected outcomes: detection/alert on unauthorized boot changes; repeatable rebuild process
- Success criteria: confirmed restoration of trusted boot chain and absence of persistence
