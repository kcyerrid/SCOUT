## Summary
System Checks (T1497.001) focuses on identifying virtualization/sandbox conditions via system-level artifact discovery (hardware identifiers, drivers/services, processes, modules, file/registry artifacts) and changing execution accordingly (exit, delay, or reduced functionality).

## Technical Overview
Typical system-check behaviors:
- **Host profiling**: CPU count/RAM size, BIOS/vendor strings, motherboard/disk identifiers, presence of VM tools.
- **Artifact hunting**: known VM/sandbox files, drivers, services, registry keys, and modules.
- **Process/module scanning**: enumerating running processes and loaded libraries for analysis tooling or VM integrations.
- **Burst execution**: multiple checks in quick succession early in runtime, often before any overt malicious actions.

The defensive value is in detecting:
- **Speed + breadth** of checks (unusual for normal user software in short windows).
- **Stage gating** (checks precede payload deployment).

## Subtechnique Considerations
Compared to other T1497 subtechniques:
- **More “recon-like” telemetry** (system enumeration), but often more detectable by burst correlation.
- Typically higher **module/process access** signals due to scanning loaded components or interacting with system interfaces.
- Pair detections with downstream behaviors (networking, persistence) to increase confidence.

## Procedure Examples
MITRE procedure examples include a wide range of malware and actor use, such as:
- Checking for VM-related tools/processes and exiting if present.
- Searching for registry keys or files associated with virtualization and sandbox products.
- Performing multiple system discovery checks to determine environment fidelity.

(See MITRE’s T1497.001 procedure examples for specific software/actors.)

## Detection Guidance
Primary analytic approach: **short-window correlation** of system discovery activity consistent with VM detection.

High-signal patterns:
1. **Discovery burst**: rapid sequence of system checks (CPU/RAM, registry keys, running processes, installed programs) immediately after a new process starts.
2. **Unusual parentage**: office apps, browsers, scripting engines, or installers spawning system-profiling bursts.
3. **Module + access coupling**: process creation plus module loads plus process access in tight windows can indicate scanning and probing.
4. **Abort behavior**: process exits/idle soon after discovery burst, especially if repeated across hosts.

### Data Source Notes
MITRE’s detection strategy **DET0168** highlights log sources including:
- **Process Creation (DC0032)** (e.g., Sysmon EventCode 1 on Windows; execve/auditd on Linux; macOS unified log process spawns),
- **Module Load (DC0016)** (e.g., Sysmon EventCode 7),
- **Process Access (DC0035)** (e.g., Sysmon EventCode 10),
with logic focused on rapid system enumeration sequences and parent/ancestry context.

## Response Guidance
1. Capture process tree, command-line, loaded modules, and process access telemetry around initial execution.
2. Determine whether checks preceded any staged payload or network activity (look for “quiet” first-stage loader patterns).
3. Hunt for the same binary/hash and early-exit behavior across endpoints and sandbox pipelines.
4. If confirmed malicious, contain and investigate follow-on techniques (persistence, C2).

## SOC Relevance
Very relevant to:
- Loader triage (first-stage often “does nothing” except check environment).
- Sandbox pipeline integrity (false negatives when samples self-suppress).
- Threat hunting for early-stage execution anomalies.

## Threat Actor Usage
MITRE includes actor use in procedure examples; treat system-check evasion as broadly used across intrusion sets and criminal ecosystems.

## Campaign Usage
Not specifically campaign-unique; commonly embedded in staged delivery chains.

## Malware Usage
MITRE procedure examples include multiple malware families performing system checks prior to executing next stages; use these examples to seed detection content and hunt pivots.

## Mitigations
MITRE notes this technique is not easily mitigated preventively due to reliance on legitimate system features. Emphasize:
- Endpoint telemetry coverage for process/module/access events.
- Detection strategies that flag atypical bursts and early exits.
- Sandbox realism improvements to reduce evasion success.

## Testing & Validation
- Run a benign test program that performs rapid system enumeration steps (platform-appropriate) and exits; validate burst detection and enrichment.
- Validate Windows coverage for Sysmon Event IDs commonly used in DET0168 (process create, module load, process access).
- Validate Linux/macOS equivalents for rapid exec bursts.
