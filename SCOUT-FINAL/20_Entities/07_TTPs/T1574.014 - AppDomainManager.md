# T1574.014 – AppDomainManager

## 1. Technique Overview
**AppDomainManager (T1574.014)** is a sub-technique of **Hijack Execution Flow (T1574)** in **MITRE ATT&CK v18**. Adversaries may execute malicious payloads by **hijacking how the .NET `AppDomainManager` loads assemblies**. The .NET runtime uses `AppDomainManager` to create and manage application domains inside a process; by manipulating configuration and loading behavior, attackers can cause **attacker-controlled .NET assemblies** to load and execute within a legitimate .NET process. :contentReference[oaicite:1]{index=1}

This is especially relevant in environments where .NET applications are common (enterprise endpoints, line-of-business apps, and management tooling), and where defenders rely heavily on process lineage rather than deep .NET runtime visibility.

## 2. Adversary Objectives
Adversaries use AppDomainManager hijacking to:
- Execute malicious code **inside trusted .NET processes**
- Establish **stealthy persistence** tied to application execution
- Support **defense evasion** by reducing obvious loader/implant artifacts
- Potentially facilitate **privilege escalation** when targeting elevated .NET processes

## 3. Common Abuse Patterns
- Configuring a malicious `AppDomainManager` to load attacker assemblies at runtime
- Leveraging .NET configuration and initialization behaviors to influence assembly resolution/loading
- Targeting frequently executed .NET binaries (business apps, utilities, management agents) to maximize trigger opportunities
- Using signed or reputable host processes to mask malicious behavior (process masquerade via “good” .NET host)

## 4. Detection Considerations
Detection depends on **module/assembly load visibility and .NET-specific telemetry**, including:
- Monitoring for **unexpected .NET assembly loads** within processes that normally do not load custom assemblies
- Correlating .NET process start with **early-stage network activity** or unusual child process creation
- Watching for **new/modified configuration artifacts** that influence .NET initialization and loading behavior
- Using EDR capabilities that surface **managed (.NET) module loads**, not just native DLL loads :contentReference[oaicite:2]{index=2}

## 5. Defensive Mitigations
- Limit and monitor write access to directories that contain .NET application binaries and configuration
- Baseline expected .NET assembly load behavior for high-value apps and admin tooling
- Enforce application control and integrity monitoring for enterprise .NET applications
- Increase logging/telemetry coverage for .NET runtime behaviors (module load, managed assembly load where supported)

## 6. Operational Impact
If successful, T1574.014 can:
- Provide **low-noise execution** within legitimate .NET applications
- Enable repeated execution (persistence) without classic autorun artifacts
- Obscure malicious activity behind trusted process contexts
- Complicate incident response due to reliance on runtime-managed behaviors

## 7. Analyst Notes
AppDomainManager abuse is a strong example of **“runtime-native” execution hijacking**: the attacker wins not by dropping a new autorun entry, but by **co-opting legitimate runtime initialization**. In investigations, prioritize (1) **how the .NET process was configured**, (2) **what assemblies were loaded**, and (3) whether early runtime activity (network, script engine, process spawn) deviates from baseline.
