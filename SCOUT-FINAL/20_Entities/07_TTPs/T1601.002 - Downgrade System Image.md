# Modify System Image: Downgrade System Image (T1601.002)

## 1. Summary
Downgrade System Image describes adversaries **replacing or reverting a system image to an older, less secure version** (or otherwise forcing a deployment pipeline to use an outdated image) to reintroduce known vulnerabilities, remove security improvements, or restore attacker-favorable configurations. This can enable persistence and facilitate follow-on compromise at scale.

Adversaries use this technique to:
- Reintroduce exploitable vulnerabilities that were patched in newer images
- Roll back security tooling, hardening, or telemetry improvements
- Restore previously implanted persistence contained in older images
- Undermine defender trust in “clean rebuild” recovery actions

---

## 2. Technical Overview
System images serve as the baseline for OS provisioning, VM templates, container base images, and appliance firmware. Downgrade operations may occur through:

- Re-pointing deployment pipelines (CI/CD, IaC, imaging systems) to older image versions
- Reverting image repositories/tags to prior revisions
- Restoring older golden images or templates to “known working” states
- Replacing signed/approved images with older, still-valid but insecure images (where policy allows)

Common targets:
- Golden images used for endpoint or server provisioning
- Cloud VM templates and machine images
- Container base images in registries (tag rollback / digest substitution)
- Network appliance or firmware images

Indicators include:
- Image version regressions (newer → older) without approved change records
- Rollback activity in image repositories, registries, or build pipelines
- Newly deployed hosts missing expected hardening controls or agents
- Resurgence of vulnerabilities previously remediated

---

## 3. Subtechnique Considerations
Key considerations for T1601.002:
- Downgrades can be subtle when versioning is weak (e.g., mutable tags like `latest`)
- “Rollback” may be framed as operational recovery, complicating triage
- Downgrade impact scales with how widely the image is used
- Often paired with trust subversion and defense impairment to reduce detection and prevention

This technique primarily attacks **image governance and provenance controls**, not endpoints directly.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Changing a provisioning pipeline to deploy a previous image revision
- Reverting a VM template library to older “stable” images
- Rolling back container base image tags to older vulnerable layers
- Restoring older appliance firmware images that lack security fixes

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should emphasize **version-control integrity, provenance, and drift**:
- Detect image version regressions in deployment pipelines and repositories
- Alert on changes to image references (IDs, digests, tags) in IaC or CI/CD
- Validate that newly provisioned hosts match approved image manifests
- Identify missing hardening baselines and security agents post-deployment

### Data Source Notes
- **Repository access logs**: Who changed image references and when
- **Image modification logs**: Track downgrades/rollbacks
- **OS installation logs**: Identify deployed image versions
- **Boot integrity monitoring**: Detect unauthorized baseline changes

Common false positives:
- Legitimate rollbacks during failed upgrades
- Disaster recovery exercises
- Emergency operational restores

Tuning guidance:
- Require approvals for any image rollback/downgrade
- Enforce immutable digests for image selection (avoid mutable tags)
- Elevate severity when downgrades follow suspicious authentication or incident activity

---

## 6. Response Guidance
When suspected:
1. Identify the downgraded image(s) and all dependent deployments
2. Quarantine/disable the outdated images and prevent further rollout
3. Redeploy impacted systems from approved, current images
4. Reassess exposure to reintroduced vulnerabilities and re-harden hosts
5. Investigate who/what modified image references (pipeline compromise vs. identity abuse)

## 8. SOC Relevance
T1601.002 is high impact because:
- It can silently reintroduce “solved” vulnerabilities at scale
- It undermines rebuild-based recovery and containment strategies
- Endpoint detections may not reveal the root cause if compromise is baked into the baseline

SOC teams should treat **image version regressions as high-severity governance events**.

---

## 9. Threat Actor Usage
Commonly used by:
- Supply-chain–oriented adversaries
- Actors targeting IT/OT provisioning pipelines
- Intruders seeking stealthy persistence through rebuild-resistant mechanisms

---

## 10. Campaign Usage
Observed in:
- Supply chain compromise scenarios
- Long-dwell infrastructure intrusions
- Post-incident re-entry attempts via rollback paths

---

## 11. Malware Usage
Associated with:
- Preinstalled persistence delivered via older images
- Backdoors embedded in baseline templates
- Minimal malware on endpoints (control-plane/pipeline compromise dominates)

---

## 12. Mitigations
Recommended mitigations:
- Enforce signed, immutable images and digests (no mutable tags for production)
- Implement strict approvals and segregation of duties for image rollbacks
- Continuous drift detection between deployed hosts and approved baselines
- Strong access controls and monitoring over image repos, registries, and pipelines

---

## 13. Testing & Validation
Validation approaches:
- Simulate controlled image rollback in non-production environments
- Validate alerts on version regressions and image reference changes
- Test IR procedures for rapid quarantine and redeployment
- Confirm governance controls prevent unapproved rollbacks

Include:
- Preconditions: controlled image repo and logging enabled
- Required roles/tools: repo admin audit access, IaC pipeline logs
- Expected outcomes: alerts on rollback + deployment drift
- Success criteria: rollback detected, blocked, and remediated
