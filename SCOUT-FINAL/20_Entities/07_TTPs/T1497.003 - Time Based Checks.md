## Summary
Time Based Checks (T1497.003) uses sleep/delay loops and timing validation to evade short-lived sandboxes or detect time acceleration. Adversaries may postpone follow-on actions (download, injection, persistence) until a delay completes or timing properties look “real.”

## Technical Overview
Common behavioral themes:
- **Delay primitives**: sleep calls, ping/timeout loops, or staged “dormancy” periods.
- **Time validation**: comparing expected vs observed elapsed time around sleeps/timers to detect acceleration.
- **Stage separation**: long pause after initial execution, then later execution of sensitive behaviors.

Defender challenge: delays are legitimate in many applications; detection requires context (process reputation, parentage, follow-on activity, and unusual durations).

## Subtechnique Considerations
Relative to other T1497 variants:
- Time checks can be **highly generic** (many benign uses), so prioritize:
  - suspicious parent/child lineage,
  - unsigned/low-prevalence binaries,
  - and correlation with later malicious stages.
- Combine with “next-stage within X minutes after delay” correlation to reduce noise.
- Don’t over-tune to specific APIs/commands; focus on behavior sequences.

## Procedure Examples
MITRE procedure examples include:
- Malware delaying second-stage downloads or activation after a specified time.
- Campaign tooling collecting timing values to detect sandbox/VM acceleration.
- Long dormancy periods after initial access before activation.

(See MITRE’s T1497.003 procedure examples for specific software/campaign references.)

## Detection Guidance
Core detections should model **delay → stage transition**.

High-signal patterns:
1. **Suspicious delay + sensitive action**: process exhibits extended delays, then performs network connections, persistence, credential access, or lateral movement behaviors.
2. **Sleep loops in scripts**: repeated looped delays preceding file writes or outbound connections.
3. **Module/load patterns**: long pause followed by unusual module loads or injection-adjacent behaviors (platform-specific).
4. **macOS timing calls**: OS API execution artifacts indicating timer/sleep usage in non-interactive binaries followed by disk/network activity.

### Data Source Notes
MITRE detection strategy **DET0141** highlights log sources including:
- **Process Creation (DC0032)** and **Module Load (DC0016)** on Windows,
- **Process Creation (DC0032)** plus **File Metadata (DC0059)** on Linux for “sleep then write” patterns,
- **OS API Execution (DC0021)** on macOS for timer/sleep API signals,
with correlation fields such as sleep duration thresholds and time to next observable event.

## Response Guidance
1. Confirm whether delays are intentional evasion vs normal application behavior (baseline common apps).
2. Pivot on:
   - file hash prevalence and signer,
   - command-line, parent process, and initial execution source,
   - what happens immediately after the delay (network/process/file changes).
3. If malicious indicators exist, contain and scope: identify other hosts running the same dormant binary and check for scheduled execution or persistence.

## SOC Relevance
High relevance because:
- Commonly defeats automated detonation windows.
- Produces “delayed” alerts where initial execution looks benign.
- Strong hunting value when paired with suspicious lineage and post-delay behaviors.

## Threat Actor Usage
MITRE procedure examples include actor/campaign ecosystems leveraging timing-based checks, including references tied to **Lazarus Group** context in campaign usage.

## Campaign Usage
MITRE procedure examples include **Operation Dream Job** context for time-checking behavior (see T1497.003 examples).

## Malware Usage
MITRE procedure examples include malware families that implement delays/dormancy before next-stage activity; use these to seed enrichment and retrospective hunts.

## Mitigations
MITRE notes preventive mitigation is difficult since this abuses legitimate system features. Practical steps:
- Detect and prioritize **delay + stage transition** sequences.
- Increase visibility into long-running processes and “late-blooming” network activity.
- For sandboxing, extend observation windows selectively for suspicious samples (risk-based).

## Testing & Validation
- Validate detections with benign programs/scripts that sleep for variable intervals and then perform a clearly logged benign action (file write or network request).
- Ensure telemetry supports “time to next event” correlation across Windows/Linux/macOS per DET0141 log sources.
- Confirm alerting captures both the delay phase and the post-delay action chain.
