# Impair Defenses: Disable or Modify Linux Audit System (T1562.012)

## 1. Summary
Disable or Modify Linux Audit System describes adversaries **tampering with Linux auditing mechanisms**, most commonly `auditd`, to suppress security-relevant event logging. By impairing audit logging, attackers reduce host-level visibility into process execution, file access, privilege use, and policy violations.

This technique is used to:
- Conceal malicious command execution
- Prevent forensic reconstruction
- Evade host-based detections relying on audit logs
- Support long-dwell or stealth-focused Linux intrusions

---

## 2. Technical Overview
Linux auditing is typically implemented via the **Linux Audit Framework** and managed by `auditd`. Adversaries impair this system by:

- Stopping or disabling the `auditd` service
- Clearing or modifying audit rules
- Replacing or corrupting audit configuration files
- Blocking audit event delivery
- Preventing auditd from restarting after reboot

Typical indicators and artifacts include:
- `auditd` service stopped or disabled
- Missing or altered audit rules
- Sudden gaps in audit logs
- Kernel audit messages suppressed or absent

---

## 3. Subtechnique Considerations
Key considerations for T1562.012:
- Requires elevated (root-level) privileges
- Often paired with **Indicator Removal on Host (T1070)**
- Common in hands-on-keyboard Linux intrusions
- Particularly impactful in environments relying on auditd for compliance or detection

Disabling audit logging is rarely legitimate outside controlled maintenance windows.

---

## 4. Procedure Examples
Representative adversary behaviors include:
- Disabling audit services prior to executing malicious commands
- Removing audit rules that log privilege escalation or file access
- Preventing auditd from starting at boot
- Modifying audit configurations to reduce coverage

*(Examples are representative and intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should focus on **audit system integrity**:
- Alert on auditd service stop or disable events
- Monitor changes to audit rule configuration files
- Detect gaps or drops in audit event volume
- Correlate audit impairment with suspicious process execution

### Data Source Notes
- **Auditd logs**: Primary detection source
- **Service configuration logs**: Detect auditd tampering
- **EDR telemetry**: Identify execution during audit gaps

Common false positives:
- System maintenance or tuning
- Kernel upgrades requiring audit restarts

Tuning guidance:
- Require change approval for audit configuration changes
- Baseline expected audit rules and service state

---

## 6. Response Guidance
When suspected:
1. Verify auditd service status and rule integrity
2. Restore baseline audit configuration
3. Preserve available logs immediately
4. Investigate actions taken during audit gaps
5. Consider host rebuild if extensive tampering is identified

## 8. SOC Relevance
T1562.012 is **highly relevant for Linux-heavy environments**. Loss of audit logging significantly degrades host-level detection and compliance monitoring.

Any unexplained auditd disruption should be treated as a **security incident**.

---

## 9. Threat Actor Usage
This technique is commonly used by:
- Advanced persistent threat groups
- Ransomware operators targeting Linux servers
- Actors conducting long-dwell intrusions

Its use indicates **deliberate defense evasion**.

---

## 10. Campaign Usage
Observed in:
- Linux server compromises
- Cloud and container host intrusions
- Espionage-focused campaigns

---

## 11. Malware Usage
Associated with:
- Linux backdoors
- Post-exploitation frameworks
- Operator-driven intrusions leveraging native tools

---

## 12. Mitigations
Recommended mitigations:
- Monitor and protect auditd service state
- Enforce immutable audit configurations
- Forward audit logs to centralized storage
- Restrict root-level access
- Validate audit coverage regularly

---

## 13. Testing & Validation
Validation approaches:
- Simulate auditd service stoppage in lab environments
- Validate alerts on audit rule changes
- Test SOC response to audit logging gaps
- Ensure alternate telemetry sources compensate for audit loss
