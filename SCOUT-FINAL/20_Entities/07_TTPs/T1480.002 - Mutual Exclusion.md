# Execution Guardrails: Mutual Exclusion (T1480.002)

## 1. Summary
Mutual Exclusion describes adversaries **using locking mechanisms to ensure only one instance of malware executes at a time**, or to prevent execution when specific conditions are detected. This technique helps adversaries avoid conflicts, reduce instability, and evade detection by analysis tools.

T1480.002 is commonly used to:
- Prevent multiple concurrent executions
- Detect sandbox or analysis environments
- Avoid drawing attention through redundant activity
- Control execution flow across infected systems

---

## 2. Technical Overview
Mutual exclusion is typically implemented using **operating system–provided synchronization primitives**. Adversaries may:
- Create named mutexes or semaphores
- Lock files or directories
- Use registry keys or system resources as locks
- Check for the presence of existing malware instances

Common technical implementations include:
- Windows mutexes via `CreateMutex`
- File locks on Unix-like systems
- Registry-based locking mechanisms
- Shared memory flags

Artifacts often include:
- Named mutex objects
- Locked files or registry keys
- Execution halted after lock detection
- Consistent lock names across infected hosts

---

## 3. Subtechnique Considerations
Key considerations for T1480.002:
- Lock names may encode campaign or victim identifiers
- Can be used both for stability and evasion
- Often combined with environmental keying
- Detection depends on visibility into OS-level objects

Mutual exclusion logic is frequently reused across malware families.

---

## 4. Procedure Examples
Observed adversary procedures include:
- Creating a mutex to prevent reinfection
- Using lock files to coordinate multi-stage payloads
- Preventing execution if analysis artifacts are present
- Using exclusion checks to avoid honeypots

These checks typically occur at the beginning of execution.

---

## 5. Detection Guidance
Detection strategies should focus on:
- Monitoring creation of named mutexes
- Detecting repeated execution attempts that terminate early
- Correlating mutex names across hosts
- Identifying unusual lock usage by user-level processes

### Data Source Notes
- **API telemetry**: Critical for mutex creation detection
- **Registry monitoring**: Useful for registry-based locks
- **File monitoring**: Required for lock-file detection

---

## 6. Response Guidance
When suspected:
1. Capture execution telemetry and lock artifacts
2. Identify mutex or lock naming patterns
3. Search for additional instances across the environment
4. Remove locks if required for remediation
5. Investigate for follow-on techniques
