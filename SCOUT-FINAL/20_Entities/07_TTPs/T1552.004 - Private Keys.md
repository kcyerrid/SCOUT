## 1. Summary
Adversaries may search for and obtain private cryptographic keys (e.g., SSH keys, code-signing certificates, PKCS#12 bundles, device identity keys, network device PKI exports) to authenticate as a user/device, decrypt protected data, sign artifacts, or pivot to additional resources. Private keys are frequently high-impact “single points of failure” because possession can bypass MFA and persist beyond password rotation if not rapidly revoked.

## 2. Technical Overview
Private key exposure commonly occurs via:
- **User key stores** (e.g., `~/.ssh` on *nix/macOS, user profile `.ssh` on Windows)
- **Certificate stores / key containers** (OS or application-managed; exportable certificates; token-signing/decryption certs on identity infrastructure)
- **Backup artifacts & exports** (PKCS#12/PFX/P12, PEM, PPK, GPG/PGP keyrings, key archives)
- **Network device PKI operations** (private key export via network device management interfaces/CLI when enabled)

Post-compromise, adversaries typically:
- Enumerate likely key locations and extensions
- Exfiltrate or stage key material
- Use keys for **remote service authentication**, **device/service impersonation**, **lateral movement**, and/or **data decryption/signing**

## 3. Subtechnique Considerations
- Keys may be **password-protected**; adversaries often pair key theft with credential access attempts elsewhere (e.g., captured passphrases, reused passwords).
- **Certificate private keys** have disproportionate impact (token signing/decryption, code signing, mTLS client auth, SSO assertions).
- **Network devices** introduce unique telemetry constraints; key export may only be visible in AAA logs or device audit trails.
- **Cloud/IdP contexts**: device identity keys and token-related certificates can enable impersonation if exported from managed systems.

## 4. Procedure Examples
Observed usage includes:
- Searching for SSH keys and other private key artifacts on endpoints
- Exporting or extracting keys/certificates from certificate stores or identity infrastructure
- Collecting keys for VPN/crypto wallets or for signing/decryption operations
- Using stolen SSH keys to propagate within environments

## 5. Detection Guidance
Prioritize detections that combine **discovery + access + staging/exfil** signals:

**Endpoint-focused signals**
- File access to **private key directories** and **certificate-related extensions** by non-interactive or unusual processes
- Processes reading from certificate/key stores followed by compression, archive creation, or outbound network connections
- Unexpected access to key material by scripting engines, remote management tools, or newly dropped binaries

**Identity/PKI-focused signals**
- Unexpected export events from certificate/key management tooling (including identity infrastructure certificate retrieval)
- Access to token signing/decryption certificate material from AD FS / federation services hosts outside normal maintenance windows

**Network device signals**
- Administrative sessions performing PKI export operations inconsistent with baseline change activity
- Correlation of AAA events (new admin source, unusual method, unusual time) with PKI-related commands

### Data Source Notes
- High-value telemetry: **file access auditing** on key directories, **process telemetry** (image, parent, command line), **certificate store access**, **administrative audit logs** on identity infrastructure, **network device AAA/audit logs**.
- Where full file read telemetry isn’t available, use **directory enumeration + subsequent archive/exfil patterns** as a proxy.

## 6. Response Guidance
1. **Containment**
   - Isolate affected hosts (especially identity/PKI servers) and restrict outbound connectivity if exfiltration is suspected.
2. **Key revocation & rotation**
   - Revoke/rotate exposed keys/certificates immediately; invalidate trust chains where necessary (e.g., replace signing certs, rotate mTLS client certs).
3. **Access review**
   - Audit successful authentications that could have used the stolen keys (SSH, VPN, mTLS, signing events).
4. **Scope expansion**
   - Hunt for additional key material in backups, shared repos, automation artifacts, and engineer/admin workstations.
5. **Hardening**
   - Make keys non-exportable where feasible; move to HSM/TPM-backed storage; enforce least privilege and strong passphrases.

## 8. SOC Relevance
**High signal** because private keys can enable durable access with minimal noise once obtained.
- Best SOC outcomes come from **early detection** of key access/staging rather than post-facto authentication anomalies.
- Pair detections with **asset criticality** (PKI/IdP servers, engineer/admin endpoints) and **egress monitoring**.

## 12. Mitigations
- **M1047 - Audit**: Regularly review access to key material and certificate stores; alert on anomalies.
- **M1041 - Encrypt Sensitive Information**: Prefer hardware-backed key storage (TPM/HSM) over local files.
- **M1027 - Password Policies**: Enforce strong passphrases for private keys; disallow weak or empty passphrases.
- **M1022 - Restrict File and Directory Permissions**: Apply least privilege to key directories and PKI artifacts; reduce exportability.
