# Process Injection: VDSO Hijacking (T1055.014)

## 1. Summary
VDSO Hijacking describes adversaries **abusing the Linux virtual dynamic shared object (VDSO)** to inject or redirect code execution within a running process. The VDSO is a kernel-provided memory region mapped into user-space processes to accelerate system calls. Manipulating this region enables stealthy execution without traditional injection mechanisms.

T1055.014 is commonly used to:
- Execute code without spawning new processes or threads
- Evade userland and file-based detection
- Hijack frequently invoked system-call helper routines
- Support stealthy post-exploitation activity on Linux systems

---

## 2. Technical Overview
The VDSO is a shared memory page mapped by the kernel into each process, exposing optimized syscall entry points such as `gettimeofday` or `clock_gettime`. Adversaries hijack this mechanism by:
- Locating the VDSO base address via auxiliary vectors (`AT_SYSINFO_EHDR`)
- Modifying function pointers or code within the VDSO mapping
- Redirecting execution flow during syscall-related operations
- Leveraging writable or misconfigured memory protections

Key technical elements include:
- `/proc/self/auxv`
- ELF parsing of VDSO structures
- Kernel–user boundary abuse
- Low-level memory manipulation

Artifacts often include:
- Execution from VDSO memory regions
- Unexpected instruction pointers within kernel-mapped pages
- Syscall behavior anomalies
- Absence of disk-backed artifacts

---

## 3. Subtechnique Considerations
Key considerations for T1055.014:
- Linux-specific and kernel-adjacent
- Requires deep OS internals knowledge
- Rare but highly stealthy
- Detection depends on syscall and memory telemetry

VDSO hijacking is typically associated with highly sophisticated adversaries.

---

## 4. Procedure Examples
Observed or theorized adversary procedures include:
- Locating the VDSO ELF header at runtime
- Overwriting syscall helper routines
- Redirecting execution during time or syscall-related functions
- Pairing VDSO hijacking with ptrace or proc memory abuse

These actions typically occur post-compromise.

---

## 5. Detection Guidance
Detection strategies should focus on:
- Monitoring execution originating from VDSO memory regions
- Detecting anomalous syscall behavior
- Identifying memory permission changes on VDSO pages
- Correlating ptrace or procfs abuse with syscall anomalies

### Data Source Notes
- **Syscall telemetry**: Primary detection surface
- **Memory telemetry**: Required for VDSO integrity validation
- **Audit logs**: Useful for detecting precursor activity

---

## 6. Response Guidance
When suspected:
1. Identify affected processes and hosts
2. Isolate systems exhibiting anomalous syscall behavior
3. Capture memory for forensic analysis
4. Investigate for additional Linux injection techniques
5. Review kernel hardening and memory protection settings
