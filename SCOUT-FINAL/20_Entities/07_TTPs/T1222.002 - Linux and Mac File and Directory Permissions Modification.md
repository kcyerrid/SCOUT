# Linux and Mac File and Directory Permissions Modification (T1222.002)

## 1. Summary
Linux and Mac File and Directory Permissions Modification describes adversaries **changing file/directory permissions, ownership, or ACLs on Unix-like systems** to bypass access controls, enable tampering with protected resources, and/or impede defensive tooling. This technique often acts as an **enabler** for persistence, execution flow hijacking, credential access, or defense evasion.

---

## 2. Technical Overview
Unix-like permission models typically combine:
- **POSIX mode bits** (user/group/other with read/write/execute)
- **Ownership** (user and group)
- **Extended ACLs** (where enabled), such as POSIX ACLs on Linux

Adversaries commonly abuse:
- `chmod` (change mode / permission bits)
- `chown` (change owner)
- `chgrp` (change group)
- `setfacl` / `getfacl` (ACL manipulation, Linux)

Typical objectives:
- Make attacker-controlled principals owners of sensitive files/directories
- Grant write/execute permissions to enable binary or script replacement
- Make persistence artifacts executable
- Restrict defenders by removing read access or locking down log/config files

Artifacts often include:
- Permission or ownership changes on sensitive paths (system binaries, launch items, shell configs)
- Extended ACL changes (Linux) inconsistent with baseline
- Permission changes followed shortly by file writes and/or execution from the modified location
- Administrative utilities invoked by unusual parent processes

---

## 3. Subtechnique Considerations
Key considerations for T1222.002: :contentReference[oaicite:1]{index=1}
- Most environments see legitimate permission changes (patching, deployments), so **context and correlation** matter
- High-risk targets include:
  - Linux: `/etc`, `/usr/bin`, `/usr/sbin`, `/var/spool`, `/root`, service unit directories
  - macOS: `/Library/LaunchDaemons`, `/Library/LaunchAgents`, `/etc`, shell profile files
- Extended ACL usage may be rare in some orgs; **any `setfacl` activity** can be high-signal when not expected

---

## 4. Procedure Examples
Representative adversary patterns include:
- Changing permissions to make a dropped script executable, then triggering it via a scheduled mechanism
- Taking ownership of a protected configuration file to insert malicious directives
- Making a directory writable to stage tooling or replace binaries used in trusted execution paths
- Modifying permissions on persistence-related files (launch agents/daemons, init scripts) to enable tampering

*(Examples are intentionally non-operational.)*

---

## 5. Detection Guidance
Detection should prioritize **behavioral chains**:
- `chmod/chown/setfacl` execution → file modification → execution/service restart
- Permission changes on sensitive directories outside maintenance windows
- Changes performed by unexpected principals or via unusual parent processes (e.g., web server worker, database process)

### Data Source Notes
- **Audit logs (Linux auditd, eBPF, endpoint telemetry)**: capture syscall-level changes (`chmod`, `fchmod`, `chown`, `fchown`) and file metadata deltas
- **Process/command telemetry**: visibility into `chmod`, `chown`, `chgrp`, `setfacl` usage and parameters
- **File integrity monitoring (FIM)**: helps baseline expected permission/ownership states for critical paths

False positives commonly include:
- Patching/installation workflows
- Configuration management (Ansible, Chef, Puppet, MDM)
- Legit admin remediation

Tuning guidance:
- Baseline expected permission changes by host role and maintenance window
- Elevate alert severity when permission changes are followed by execution from the modified location

---

## 6. Response Guidance
Recommended SOC actions:
1. Identify who/what performed the permission change (user, service account, parent process)
2. Enumerate modified objects and determine whether ownership or ACLs changed
3. Check for follow-on actions: file writes, new binaries, execution, service reloads
4. Restore permissions/ownership from known-good baseline (where safe)
5. Hunt across fleet for the same permission-change patterns and paths

## 8. SOC Relevance
T1222.002 is high-impact when it affects:
- Authentication and authorization files/configs
- Persistence locations (launch agents/daemons, init scripts, shell startup configs)
- Trusted execution paths (binaries/scripts invoked by services or privileged users)
- Logging and security tooling paths (defense impairment)

This technique frequently precedes **binary/config tampering** and **persistence establishment**.

---

## 9. Threat Actor Usage
Commonly observed among:
- Linux-focused intrusion sets
- Cloud and container compromise operators
- Ransomware affiliates targeting Linux/ESXi environments (often as a precursor to maximizing access)

Confidence should be driven by corroborating telemetry (what changed, who changed it, and what happened next).

---

## 10. Campaign Usage
Observed in:
- Web server compromise chains (permission changes enabling payload staging and execution)
- Cloud workload intrusions (permission changes to persistence paths)
- Post-exploitation phases where attackers prepare environment for follow-on actions

---

## 11. Malware Usage
Often associated with:
- Loaders and scripts that require executable permission changes
- Backdoors that modify config files under `/etc` or launch locations
- Ransomware operations seeking broad file access or tampering with links/paths

---

## 12. Mitigations
Recommended mitigations: :contentReference[oaicite:2]{index=2}
- Enforce least privilege and restrict root/admin access
- Apply restrictive permissions and correct ownership on critical system paths
- Use FIM to monitor permission/ownership state changes
- Restrict use of ACL tools (`setfacl`) to authorized workflows
- Harden macOS persistence locations and monitor LaunchAgent/Daemon directories

---

## 13. Testing & Validation
Validation approaches:
- Confirm you collect permission/ownership change telemetry (auditd/eBPF/EDR)
- Perform controlled permission changes on representative systems and validate alerting
- Validate correlation logic: permission change → write → execute
- Use safe adversary emulation and purple-team exercises to test end-to-end detection/response

## 15. Notes
- In Unix-like environments, permission changes are common; prioritize detections that correlate to follow-on writes/execution.
- Treat `setfacl` activity as high-signal where extended ACLs are uncommon.
- For macOS, baseline and monitor LaunchAgent/LaunchDaemon directories for both content and permission drift.
