## Summary
**Weaken Encryption: Disable Crypto Hardware (T1600.002)** describes adversaries disabling dedicated cryptographic hardware on network devices, potentially degrading encryption performance and/or influencing cipher negotiation behavior to weaken protections. 

## Technical Overview
Many routers/firewalls leverage hardware acceleration for cryptographic operations (IPsec, TLS offload, etc.). Disabling crypto hardware may:
- force fallback to software crypto paths,
- reduce throughput and change operational constraints,
- create conditions enabling weaker cryptographic choices (depending on device/platform behavior and configuration).

Defender-observable outcomes may include:
- config/CLI actions targeting hardware crypto settings,
- status changes in crypto engines/modules,
- performance/throughput anomalies and unexpected traffic negotiation changes.

## Subtechnique Considerations
This is a subtechnique of **T1600 Weaken Encryption**.   
Use this note when you have evidence of **crypto acceleration/module disablement** rather than explicit key-size/cipher downgrades.

## Procedure Examples
Defender-relevant examples include:
- Commands or configuration changes that disable crypto acceleration/engines.
- Firmware/config modifications referencing crypto hardware modules.
- Sudden, unexplained degradation in encrypted traffic throughput consistent with loss of acceleration. 

## Detection Guidance
MITRE’s detection strategy highlights observing anomalous CLI commands, unexpected firmware/config updates, and traffic anomalies consistent with disabled crypto hardware. 

High-signal detection angles:
1. **CLI/config change monitoring**
   - Alert on changes to crypto engine/acceleration features, especially outside change windows.
2. **Control-plane + performance correlation**
   - Join “crypto hardware disabled” events with sudden drops in VPN/TLS throughput or CPU spikes.
3. **Network behavior deltas**
   - Watch for cipher negotiation shifts or protocol fallbacks after crypto engine status changes.

### Data Source Notes
Relevant ATT&CK telemetry categories include **Command**, **File**, and **Network Traffic**.   
MITRE detection strategy log sources emphasize:
- command execution (network device CLI),
- file/config modification (networkdevice:config),
- network traffic content/flow indicators post-change. 

## Response Guidance
1. **Validate the change**
   - Confirm crypto engine/acceleration status and the exact config delta.
2. **Identify origin**
   - Attribute to admin account/session; correlate with AAA logs and PAM tooling.
3. **Restore**
   - Re-enable approved crypto hardware settings; apply golden configuration.
4. **Hunt for follow-on**
   - Check for other defense-evasion actions on the device (logging changes, firmware tampering, new accounts).
5. **Hardening**
   - Tighten privileged access, enforce approvals, and enable immutable/audited config pipelines.

## SOC Relevance
This subtechnique can be a **high-fidelity indicator** because disabling crypto hardware is uncommon in normal operations and typically gated behind privileged workflows. It’s especially SOC-relevant if paired with:
- new/unknown admin sessions,
- concurrent logging reductions,
- unexpected firmware events,
- downstream negotiation/throughput anomalies.

## Mitigations
- Enforce privileged change controls for crypto hardware/acceleration settings.
- Monitor crypto engine state and alert on disablement.
- Baseline encrypted throughput and device CPU usage; alert on sharp deviations.
- Use signed firmware and restrict firmware upgrade paths to approved sources.

## Testing & Validation
- In lab/nonprod, perform an authorized toggle of crypto hardware/acceleration and validate:
  - CLI/config logs capture the action (user/source),
  - SOC rule triggers on the change,
  - performance/throughput baselines detect deviation.
- Exercise rollback procedures and confirm posture restoration.
