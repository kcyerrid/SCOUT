# Compromise Software Supply Chain (T1195.001)

## 1. Summary
Compromise Software Supply Chain describes adversary manipulation of legitimate software products, updates, or distribution mechanisms to deliver malicious code to downstream customers. By abusing trusted software delivery paths, adversaries inherit the trust relationship between vendors and consumers, enabling large-scale initial access with minimal user interaction.

This subtechnique is particularly impactful due to its potential for widespread, stealthy distribution.

---

## 2. Technical Overview
Adversaries compromise software supply chains by:
- Injecting malicious code into legitimate application source code
- Backdooring software updates or installers
- Compromising update servers or distribution infrastructure
- Abusing code-signing processes to deliver trusted malware

Artifacts may include signed binaries exhibiting malicious behavior, unexpected update behavior, anomalous outbound connections from trusted software, and deviations in build artifacts.

---

## 3. Subtechnique Considerations
T1195.001 focuses specifically on **software products and updates**, distinguishing it from:
- Hardware supply chain compromise
- Dependency or development tool compromise

Detection is often delayed because malicious software appears legitimate and trusted by endpoint and network controls.

---

## 4. Procedure Examples
Observed adversary procedures include:
- Backdooring vendor software updates
- Modifying installer packages prior to distribution
- Compromising vendor build systems to inject malicious payloads
- Leveraging compromised update mechanisms for command-and-control

Analysts may observe malicious activity originating from signed or widely deployed software.

---

## 5. Detection Guidance
Detection should emphasize integrity and behavioral monitoring:
- Behavioral anomalies from trusted applications
- Unexpected network connections following software updates
- Hash or signing changes in distributed binaries
- CI/CD activity inconsistent with baseline workflows

Signature-based detection alone is insufficient for this subtechnique.

### Data Source Notes
- **Application Logs:** Useful for identifying abnormal behavior post-update
- **Code Repository Logs:** Critical for detecting unauthorized code changes
- **CI/CD Logs:** High value for detecting build pipeline compromise

---

## 6. Response Guidance
When software supply chain compromise is suspected:
- Immediately halt software distribution and updates
- Identify affected software versions and customers
- Revoke compromised signing certificates
- Coordinate with vendors, customers, and regulators as required

Preserve build artifacts, update packages, and logs for forensic analysis.

## 8. SOC Relevance
Software supply chain compromise represents one of the highest-impact initial access vectors. Detection maturity is typically low, making proactive integrity monitoring and vendor security assurance critical for SOC effectiveness.

---

## 9. Threat Actor Usage
This subtechnique has been used by:
- Nation-state actors conducting strategic espionage
- Advanced threat groups targeting technology providers
- Highly capable adversaries seeking scalable access

Confidence in usage by advanced actors is high.

---

## 10. Campaign Usage
Compromise of software supply chains has appeared in:
- Large-scale espionage operations
- Strategic access campaigns against software vendors
- Long-dwell intrusions with broad downstream impact

---

## 11. Malware Usage
Malware delivered via software supply chain compromise often manifests as:
- Backdoored legitimate applications
- Signed loaders embedded in updates
- Trusted binaries repurposed for command-and-control

Post-compromise tooling frequently includes:
- [[30_CIPHER/05_Malware/S0154 - Cobalt Strike|Cobalt Strike]]

---

## 12. Mitigations
Effective mitigations include:
- Securing build and release pipelines
- Enforcing strong code-signing controls
- Software composition analysis (SCA)
- Continuous monitoring of trusted software behavior
- Vendor security audits and attestations

---

## 13. Testing & Validation
Validation approaches include:
- Red team simulations of compromised updates
- Integrity monitoring tests for build artifacts
- Purple team exercises focused on trusted software abuse

Successful validation detects anomalous behavior originating from trusted binaries.
