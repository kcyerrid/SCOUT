# T1110.003 - Password Spraying

## 1. Summary
Password Spraying (T1110.003) is a brute force subtechnique where adversaries try one (or a small set of) commonly used passwords against many accounts to reduce the chance of triggering lockouts associated with repeated failures on a single account. It is frequently observed against exposed remote access and SSO/IdP endpoints.

## 2. Technical Overview
Typical spray pattern:
- Choose a small password set (often seasonal/organizational themes) likely to meet complexity policy.
- Iterate across a large user list (email formats, discovered accounts, public employee data).
- Throttle attempts to stay below rate/alert thresholds, often spreading across time and infrastructure.
- Target services: SSH, SMB, LDAP/Kerberos, RDP gateways, and cloud/SSO apps (including federated auth).

Key operational behavior from ATT&CK description:
- Intentional throttling to evade detections.
- Preference for auth paths that are less “loud” in certain environments (e.g., differences in logging visibility across protocols).

## 3. Subtechnique Considerations
- Parent technique: [[20_Entities/07_TTPs/TA0006 - Credential Access/T1110 - Brute Force|T1110]]
- Distinguish from:
  - **T1110.001 Password Guessing**: many passwords against one/few users.
  - **T1110.004 Credential Stuffing**: many username/password pairs from breaches.
- Spraying frequently overlaps with identity compromise workflows and may precede token abuse, mailbox access, or external remote service access.

## 5. Detection Guidance
Detection objective: **identify one/few-password-many-user patterns, including throttled or distributed variants**.

Core detections:
- **Password reuse across many users**
  - Same password (or same failure reason signature indicating same password) used across many principals in a window.
- **Many principals targeted from one source**
  - Single IP/client fingerprint causing failures across many usernames with consistent cadence.
- **Distributed spray**
  - Many IPs targeting many users with consistent user agent/client characteristics and low per-IP rate.
- **IdP/SSO-specific**
  - Conditional access failures clustered by policy outcome.
  - Increased “invalid password” outcomes across many users from new device classes/locations.
- **Edge + IdP correlation**
  - Reverse proxy/WAF “login attempts” correlated to IdP failure events.
  - Detection for “spray → first success” pivot and immediate high-risk actions.

Tuning guidance:
- Use **account population baselines** (per app) to avoid false positives from shared NATs.
- Include **user tier weighting** (admins/service accounts) and **source risk scoring** (proxy/residential).

### Data Source Notes
This technique page does not present an explicit ATT&CK “Data Sources” list in the technique header; prioritize:
- IdP sign-in logs (success/failure, CA outcomes, risk, device, geo)
- SaaS audit logs (post-auth actions after first success)
- Edge/WAF/reverse proxy logs for auth endpoints
- OS/network auth logs for SSH/SMB/RDP/LDAP/Kerberos attempts
- Network device AAA/syslog for management plane sprays

## 6. Response Guidance
- Immediately implement/raise **rate limiting** and **bot controls** for exposed auth endpoints.
- Apply **step-up MFA** and stronger conditional access for targeted apps and accounts.
- Block abusive IPs/ASNs and consider denylisting proxy/anonymizer sources where appropriate.
- Force password reset + session/token revocation for accounts that authenticated successfully during the spray window.
- Validate no persistence was established post-compromise (mailbox rules, OAuth grants, new devices, external forwarding).

Critical SOC relevance:

## 12. Mitigations
ATT&CK-listed mitigations for this subtechnique include:
- **M1036 - Account Use Policies**: lockout and conditional access constraints; restrict risky auth sources.
- **M1032 - Multi-factor Authentication**: enforce MFA broadly, especially for externally accessible apps.
- **M1027 - Password Policies**: prevent weak/default passwords; strengthen user guidance and controls.

## 13. Testing & Validation
- Validate detection for “one/few password signatures across many users,” including throttled variants.
- Red-team/authorized testing should confirm:
  - IdP telemetry completeness (failures + CA outcomes)
  - Cross-log correlation (edge ↔ IdP ↔ app)
  - Automated response safety (avoid locking out legitimate shared NAT populations)
