# T1518.001 - Software Discovery: Security Software Discovery

## 1. Summary
Adversaries enumerate **security software, defensive tools, sensors, and configurations** (including cloud monitoring agents) to assess detection risk and tailor defense evasion, persistence, or payload selection.

## 2. Technical Overview
Common discovery targets:
- AV/EDR products and agents (installed software + running components)
- Local firewall tooling and configuration indicators
- Endpoint monitoring/logging agents (including cloud VM agents)
- Forensic and analysis tools (especially on analyst/admin workstations)

Common execution modalities:
- Inventory and process/service enumeration (endpoint)
- Registry/WMI/PowerShell queries (Windows)
- Filesystem and configuration checks (macOS/Linux)
- Cloud API inspection for cloud-native monitoring/agent presence (IaaS)

## 3. Subtechnique Considerations
- This sub-technique is often **higher signal** than generic software inventory, especially when:
  - performed shortly after initial access
  - executed by suspicious parent processes (phish payloads, LOLBins, script hosts)
  - paired with follow-on defense evasion (tampering, exclusions, kill/stop operations)

## 4. Procedure Examples
MITRE procedure examples include:
- Malware and tools identifying installed AV/defensive products (e.g., [[30_CIPHER/05_Malware/S1028 - Action RAT|Action RAT]] querying installed AV products).
- Threat groups checking defensive tooling using WMI or other inventory methods (e.g., [[30_CIPHER/03_Threat_Actors/G0082 - APT38|APT38]] and [[30_CIPHER/03_Threat_Actors/G1044 - APT42|APT42]] listed on the technique page).
- Security tooling checks present across multiple families such as [[30_CIPHER/05_Malware/S1025 - Amadey|Amadey]] and [[30_CIPHER/05_Malware/S0689 - WhisperGate|WhisperGate]] (per MITRE examples).

## 5. Detection Guidance
Security tooling discovery is a strong precursor for defense evasion—treat as **high priority** when anomalous.

High-signal patterns:
- Enumeration of security products by **non-admin users**, **rare binaries**, or **workstations not used for IT/security operations**.
- Discovery executed from **macro/script chains** or immediately after suspicious downloads.
- Repeated checks for specific vendors/products (suggests environment-aware payload logic).

Detection engineering patterns:
- Alert on **inventory/process/service queries** from suspicious ancestry (Office → script host → discovery).
- Correlate discovery with:
  - subsequent stop/kill/tamper activity against security components
  - suspicious configuration changes (policy, exclusions)
  - credential access attempts within the same session

### Data Source Notes
Telemetry that typically enables reliable detections:
- **Endpoint**: process creation + command line; parent-child lineage; signed/unsigned metadata; script telemetry (PowerShell).
- **Security tooling**: EDR detections of “security product discovery” behavior categories (where available).
- **Cloud**: audit logs for API calls that enumerate agents/monitoring on instances.

## 6. Response Guidance
1. **Confirm host role**: is this a security/admin endpoint where tool checks are expected?
2. **Assess compromise likelihood**: inspect execution chain, download origin, and identity posture.
3. **Hunt follow-ons**: tampering attempts, exclusion additions, agent disablement, persistence.
4. **Contain and harden**: isolate endpoint; protect/tamper-proof security agents; rotate credentials if broader compromise is suspected.

## 12. Mitigations
Because this abuses legitimate inventory features:
- Harden endpoints with application control and restricted scripting
- Ensure tamper protection on security agents
- Reduce local admin exposure and enforce privileged access tiering
- Maintain robust process/script logging to support chaining analytics

## 13. Testing & Validation
- Validate detections using benign simulations that:
  - query installed security products from a user workstation
  - compare against sanctioned IT/security tooling activity on admin hosts
- Confirm alerts trigger based on **context** (ancestry, user, host role), not just command presence.
