## 1. Summary
Adversaries may compress or encrypt collected data using **libraries** (e.g., zlib/libzip/bzip2 APIs) embedded within malware or scripts. Compared to utility-based archiving, library-based archiving can be harder to spot because it may not spawn recognizable archiver binaries, shifting detection toward behavioral telemetry such as module loads, interpreter usage, and suspicious archive outputs.

## 2. Technical Overview
**What it is:** Archiving/encryption performed by calling compression/archival libraries directly from code (malware, scripts, or custom binaries), rather than invoking a standalone archiving utility.

**Defender-relevant behaviors:**
- Scripting or custom binaries executing and loading compression-related modules/libraries (e.g., `libz`, `libarchive`, zip APIs).
- Creation of archive outputs without a corresponding `zip/tar/7z/rar` process.
- Archive creation in staging directories followed by outbound transfer.
- In some cases, compression is applied to data before it is sent over C2, making “archive” appear as high-entropy or compressed blobs.

## 3. Subtechnique Considerations
Use this subtechnique when:
- Archive creation is accomplished **inside the process** via a library (zlib/libzip/bzip2/zip APIs), especially when no distinct archiver process exists.

If a recognizable archiver utility is executed, prefer:
- [[20_Entities/07_TTPs/TA0009 - Collection/T1560.001 - Archive via Utility|T1560.001]]

If archiving/encryption is bespoke (custom XOR/containers), prefer:
- [[20_Entities/07_TTPs/TA0009 - Collection/T1560.003 - Archive via Custom Method|T1560.003]]

## 5. Detection Guidance
Library-based archiving is best detected via **in-process indicators** and **output artifact patterns**.

**MITRE Detection Strategy (DET0268) highlights:**
- Correlate script/custom binary execution with **module loads** associated with compression/archiving libraries, followed by archive file creation.
- Identify unexpected library loads by processes that do not normally perform compression (e.g., bespoke .NET binaries, suspicious Python/Perl processes).
- Baseline known enterprise software that legitimately uses compression libraries (backup agents, browsers, package managers) to reduce false positives.

### 5.1 Data Source Notes
Primary data components from DET0268:
- **Process Creation (DC0032)**: Windows 4688, Linux/macOS process telemetry
- **Module Load (DC0016)**: Sysmon 7, auditd mmap/shared object loads, macOS dylib load observations where available
- **File Creation (DC0039)**: archive output creation in staging directories
- **Command Execution (DC0064)**: Linux interpreter execution patterns (python/perl/custom binaries) correlated with outputs

**Where EDR helps most:**
- Module/library load telemetry (zlib/libarchive/zip APIs) and process ancestry.
- File entropy and content-type classification for suspicious outputs.

## 6. Response Guidance
1. **Identify the producer process:** Determine which process created the archive output without spawning standard utilities.
2. **Collect runtime evidence:** Capture process metadata (hash, signing, command line), loaded modules, and any script content or parent process context.
3. **Preserve output artifacts:** Acquire the compressed/encrypted files, record hashes, and evaluate for sensitive data exposure (handled per policy).
4. **Look for follow-on exfil:** Correlate archive creation timestamps with outbound connections, uploads, or C2 traffic.
5. **Contain and eradicate:** Remove persistence, block related hashes, and rotate credentials if archives include secrets.

## 8. SOC Relevance
**Why SOC cares:** Library-based archiving is a common tactic for stealth: fewer obvious “archiver.exe” processes and more blending into legitimate compression use.

**Best SOC pivots:**
- Rare process + compression library load + archive output creation in staging directories.
- Interpreter activity (python/perl/powershell) coupled with unexpected compression module usage.
- High-entropy or compressed outputs created shortly before egress.

## 12. Mitigations
ATT&CK notes this technique is difficult to mitigate preventively because it abuses system features and common libraries. Emphasize detective controls and least-privilege to limit access to sensitive data.

## 13. Testing & Validation
- Validate DET0268-style detections with controlled tests that simulate compression via libraries (e.g., script execution + library usage + output creation).
- Confirm your environment can observe:
  - Module/library loads
  - Process ancestry and interpreter context
  - Output file creation metadata and entropy
